## 0. 先に結論（この設計の要点）

1. **やりたいことの大半は「既存資産の組み合わせ＋夜間バッチ化」で実現可能**。ゼロから作る必要はほとんどない。
   - 夜間バッチ基盤（Vercel Cron + service role）は **既に本番稼働中**（`/api/cron/daily-digest` 23:00、`/api/cron/xray-snapshot` 15:30）。
   - スナップショット保存・履歴・比較の型（`xray_snapshots`：`payload jsonb` に結果を丸ごと保存）も **既存**。週次報告書のスナップショット/比較はこの型を踏襲できる。
   - AIは既に `claude-opus-4-8` を Server Action から呼ぶ実装済み（議事録要約 `generateMeetingSummaryAction`）。
   - 議事録の入力口（tl;dv MCP）、下書きメール（Gmail MCP）、日程調整（Googleカレンダー MCP）、通知（Slack MCP / アプリ内 `notifications`）が **接続済み**。

2. **【確定方針・2026-07-12】AI実行は当面「Claude Code方式（方針A）」で従量課金ゼロ**。
   デプロイ済みアプリから Anthropic API（`ANTHROPIC_API_KEY`＝トークン従量課金）を呼ぶのではなく、
   **夜間に Claude Code 自身をスケジュール実行**し、MCP（Supabase / Gmail / tl;dv / カレンダー）経由で読み書きする。
   消費は **Claudeサブスクの枠内**。就寝中の時間帯に走らせることで **5時間の利用枠を有効活用** する。
   将来、即時性が必要になった機能だけ API従量方式（方針B）へ切り替える（UI/データは変えずに機能単位で昇格）。→ 詳細は §7。

3. **完全自動にしない設計を推奨**。生成物（戦略・議事録・メール文面）は必ず **「AIが下書き → 人が確認 → 送信/確定」** の関所を通す。
   特にメール送信は要望どおり **手動**（Gmail下書きまで自動、送信は営業）。これは事故（誤送信・誤情報）と信頼低下を防ぐ最重要原則。

4. **外部依存で「今すぐは自動化しきれない」ポイント**（§6の可否表で×/△）:
   - アプリ内からの **Web検索**（マーケの最新事例収集）→ 検索APIの追加が必要（Anthropic web_search / Brave / SerpAPI 等）。
   - **アイキャッチ生成**（GPT画像）→ OpenAI画像APIの追加が必要。
   - **レンタルサーバーへの記事アップロード** → 現状MCPなし。WordPress REST API か SFTP連携を別途作る（or 当面手動）。

## 1. 全体像 — 3層で捉える

営業自動化を「バラバラの機能の寄せ集め」にしないため、**3つの層**に整理する。上の層ほど資産（一度作れば効き続ける）、下の層ほど日々の流れ。

```
┌─────────────────────────────────────────────────────────────┐
│ 【資産層】 カトルセの型・Skills / ノウハウ・事例ナレッジ           │  ← B1, B7
│  ・業種×規模×役職 別の勝ち筋（プレイブック）                      │     一度作り、勝敗で育てる
│  ・成功/失敗例・成約/失注理由・ささる事例（自社/他社）             │
└───────────────▲───────────────────────────┬─────────────────┘
                │ 参照（RAG）                  │ 自動蓄積（議事録から抽出）
┌───────────────┴───────────────────────────▼─────────────────┐
│ 【自動化層】 夜間バッチ（Vercel Cron）＋オンデマンドAI            │  ← B2,B3,B4,B5,B8
│  事前リサーチ→戦略提案 / 議事録まとめ / お礼＋資料＋NA下書き        │     人は「確認」だけ
│  / タスク自動登録 / 催促・漏れ検知 / マーケ記事パイプライン         │
└───────────────▲───────────────────────────┬─────────────────┘
                │ 入力（自動連携）              │ 出力（下書き・タスク・通知）
┌───────────────┴───────────────────────────▼─────────────────┐
│ 【現場層】 商談・チェックシート・週次報告・定例会                  │  ← B5,B6
│  営業は商談とクロージングに集中。入力は最小、確認はワンクリック      │
└─────────────────────────────────────────────────────────────┘
```

**設計思想**: 営業マンの手を「入力」から「確認・判断・対面」へ移す。AIは *下書き工* に徹し、意思決定と送信は人が持つ。

## 3. 資産層の設計

### B1. カトルセの型・Skills（営業プレイブックの資産化）

**やりたいこと**: 業種・会社規模・相手役職に合わせた営業戦略を提案するため、自社の過去データと橋本さんへのインタビューから「カトルセの型（勝ち筋・トーク・質問・提案パターン）」を作り、AIが参照できる資産にする。

**必要な機能**
- **プレイブック（型）ライブラリ**: 「いつ・誰に・何を・どう」を構造化して蓄積。
  - 軸: `業種` × `会社規模` × `相手役職` × `商材/パッケージ`（既存 `solution_packages` と接続）。
  - 中身: 想定課題 / 刺さる訴求 / 初回質問リスト / 提案の流れ / よくある反論と切り返し / 決裁の勘所 / 事例の使いどころ。
- **型の作り方（2ソース）**
  1. **過去データからの自動抽出**: 成約した商談の議事録・活動・失注理由をAIで束ね、「この業種で勝った時の共通パターン」を叩き台として生成 → 人がレビューして採用。
  2. **橋本インタビューの構造化**: インタビュー音声/メモ（tl;dv or 手入力）をAIで型フォーマットに整形 → 「橋本の暗黙知」をSkills化。
- **RAG参照**: B2（事前ブリーフィング）やB7（事例レコメンド）から、案件の属性に一致する型を自動で引く。

**実現手段（既存資産の再利用）**
- 既存 `solution_packages`（提案パッケージ、お土産5種シード）を土台に、`sales_playbooks` を新設して紐付け。
- AI抽出は既存 `ai.ts` の呼び出しパターンをそのまま流用。

**データモデル（新規）**
```
sales_playbooks（型）
  id, tenant_id, title,
  industry, employee_size_band, target_role,       -- 適用条件（部分一致/NULL=汎用）
  solution_package_id (nullable),
  hypothesis_issues text,      -- 想定課題
  value_props text,            -- 刺さる訴求
  key_questions text,          -- 初回質問リスト
  proposal_flow text,          -- 提案の流れ
  objections text,             -- 反論と切り返し
  decision_tips text,          -- 決裁の勘所
  source ('interview'|'data_mined'|'manual'),
  status ('draft'|'active'|'archived'),
  win_count int, loss_count int,   -- 適用実績（学習ループ用）
  embedding vector,            -- セマンティック検索用（pgvector, §8）
  created_by, created_at, updated_at
```

**追加アイデア（勝ちパターン学習ループ）**
- 案件が成約/失注した時、**「どの型を使ったか」を記録**（`opportunities.applied_playbook_id`）。四半期ごとに「型別の成約率」を集計し、勝ってる型を昇格・負けてる型を要改訂として提示。
  → 型が *使うほど賢くなる*。属人性を下げつつ、現場の実データで磨かれる。

### B7. ノウハウ・事例ナレッジベース（蓄積と検索）

**やりたいこと**: 商談で得たノウハウ（成功/失敗）、成約理由/失注理由、ささる事例（自社/他社）が **自然に貯まり、見やすく検索できる** 状態。

**必要な機能**
- **ナレッジ・エントリ**: 種別（ノウハウ / 成約理由 / 失注理由 / 事例）× タグ（業種・課題・商材・競合）で構造化。
- **自動蓄積が肝**: 手入力に頼ると貯まらない。**議事録AI要約（B3）から「ノウハウ候補」「失注/成約理由候補」を自動抽出** → ナレッジ下書きとしてキューに積み、人が承認したら本登録。「気づいたら貯まっている」を実現。
- **検索**: キーワード全文検索＋セマンティック検索（「価格で負けた事例」等の意味検索）。案件詳細から「この相手に刺さりそうな事例」をレコメンド。
- **失注理由の構造化**: 既存バックログ C-4（`lost_reason` を選択式マスタ化）と統合。理由別・競合別・ステージ別の分析画面へ接続。

**実現手段**
- 既存 `meetings.ai_summary` の生成時に、抽出タスクを1回追加（同じAI呼び出しの中で構造化出力させ、コスト増を最小化）。
- 検索は Postgres 全文検索（`tsvector`）＋ pgvector（§8）。

**データモデル（新規）**
```
knowledge_entries
  id, tenant_id, kind ('knowhow'|'win_reason'|'loss_reason'|'case_study'),
  title, body,
  is_own_company bool,          -- 自社/他社事例の区別
  account_id (nullable), opportunity_id (nullable),
  industry, competitor, tags text[],
  source ('ai_extracted'|'manual'), status ('draft'|'approved'),
  embedding vector, search_tsv tsvector,
  created_by, approved_by, created_at
```

**追加アイデア**
- **週次で「今週の学び」ダイジェスト**をSlackに（新規ナレッジ3件をチームに自動共有）。ノウハウが個人に埋もれない。
- 事例は **マーケ（B8）の記事ネタ・商談後の送付資料** に再利用 → 「営業の学び → コンテンツ → リード」の一気通貫。

## 4. 自動化層の設計（夜間バッチ中心）

### B2. 商談前ブリーフィング（事前リサーチ・戦略提案の夜間自動生成）

**やりたいこと**: 事前リサーチと、業種/規模/役職に合わせた戦略提案を、夜間バッチで自動作成。営業は当日それを読んで商談に臨む。

**バッチの流れ（毎晩）**
1. Cronが「翌日〜数日先にアポがある案件」を抽出（既存 `opportunities.appointment_at` / `first_meeting_date`）。
2. 各案件について、案件・顧客・担当者属性 ＋ **一致する型(B1)** ＋ **過去の接点/活動** を集約。
3. AIが **商談ブリーフ** を生成：
   - 企業/相手の仮説プロフィール、想定課題、この相手に効く訴求、初回質問リスト、提案候補、想定反論と切り返し、ゴール設定（この商談で何を取るか）。
4. 結果を `meeting_briefings` に保存し、担当営業へ **当日朝にSlack DM＋アプリ内通知**（「今日のA社商談ブリーフができています」）。

**実現手段**
- 実行は **Claude Code の夜間スケジュール実行**（§7・方針A、従量ゼロ）。Routine(cron)で毎晩セッションを起動し、Supabase MCPで対象案件を読み、生成物を `status='draft'` で書き戻す。
- WO-07 6.1「商談前リサーチ」の**プロンプト設計**がそのまま生きる（実行を *即時ボタン* → *夜間バッチ* に変更）。
- 型(B1)とのRAG接続で「業種/規模/役職に合わせた」を満たす。

**実現性**: ◎（保有データからの仮説生成）。ただし **Web上の最新の企業情報** まで取るなら検索APIが必要（△、§6）。まずは *保有情報＋型* からの仮説で十分価値が出る。

**データモデル（新規）**: `meeting_briefings(id, tenant_id, opportunity_id, meeting_id, payload jsonb, generated_at, model, status)`

### B3. 商談後オートメーション（議事録・お礼・資料送付の下書き）

**やりたいこと**: 商談後、録音文字起こし/tl;dv/自分のメモを自動連携し、夜間バッチで
「議事録まとめ」＋「お礼メール下書き」＋「関連資料の送付下書き」を作る。**メール送信は営業が手動**。

**入力の自動連携（3経路）**
- **tl;dv**: tl;dv MCP（`get-meeting-transcript` / `get-meeting-notes` / `search-meetings`）で文字起こしを取得 → 案件の `meetings.minutes_detail` へ自動流し込み。
- **録音の文字起こし**: 音声ファイル→文字起こしは外部（tl;dv/Whisper等）に委ね、テキストを取り込む。
- **手メモ**: 既存の議事録入力欄にそのまま。

**バッチの流れ（毎晩）**
1. 「本日 議事録テキストは入ったが ai_summary 未生成」の商談を抽出。
2. AIで **議事録要約**（既存 `generateMeetingSummaryAction` のプロンプトを流用）＋ **ネクストアクション候補**（B4）＋ **ノウハウ/勝敗理由候補**（B7）を **1回のAI呼び出しで構造化出力**。
3. **お礼メール下書き** と **関連資料送付メール下書き**（案件の商材から `solution_packages` の資料を選定）を生成し、**Gmail下書き**（`create_draft`）として保存。
4. 担当へ通知。営業は下書きを確認・微修正して **手動送信**。

**実現手段**
- 議事録要約の**プロンプト設計は実装済み**（`generateMeetingSummaryAction`）。方針Aでは同じ設計を **Claude Codeバッチ側で実行**（§7）。既存Server Actionは方針Bの雛形として温存。
- Gmail MCP `create_draft` で下書き保存（送信はしない＝要望どおり）。
- 関連資料は `solution_packages` の資料URL/添付から選定。

**実現性**: ◎。**送信は手動**なので誤送信リスクが構造的に無い。

**追加アイデア**
- 議事録要約に **「本部（橋本）が見るべき論点」** セクションを付け、定例会アジェンダ（B6）へ自動集約。
- お礼文面は **型(B1)の訴求** を織り込み、単なる定型文でなく「次に効く一言」を入れる。

### B4. ネクストアクション & タスク & 日程調整

**やりたいこと**: 商談からネクストアクションを作りタスク登録。可能ならお礼メールにNA促し（日程調整）も同梱。

**流れ**
- B3の議事録要約から **NA候補（内容・担当・期日）** を抽出 → 既存 `tasks`（`origin='ai_meeting'` で発生源を区別、D7準拠）へ **下書きタスク** として起票。営業がワンクリック確定。
- 案件の `next_action_date/next_action_text`（既存カラム）も更新候補として提示。
- **日程調整の同梱**: お礼メール下書きに「次回◯◯を△△頃に」の一文＋候補日時。候補は Googleカレンダー MCP `suggest_time` / `list_events` で担当の空きから算出。確定アポは `create_event` で登録（既存のアポ→カレンダー連携 `0087_appointment_calendar_events` と整合）。

**実現手段**: 既存 `tasks`＋`origin`列、Googleカレンダー MCP、既存アポ・カレンダー基盤。
**実現性**: ◎（タスク自動起票）/ ○（日程調整同梱は文面生成＋空き算出の組み合わせ）。

### B5. 行動漏れ防止（催促メール＋チェックシート）

**やりたいこと**: 営業の行動漏れを、催促メールとチェックシートの両輪で防ぐ。

**(a) 催促・漏れ検知**
- 既存の **`sales_alerts` RPC**（放置案件・次回AC未設定/超過・提案後フォロー漏れ）と **daily-digest**（毎朝Slack）が既に土台。

### B6. 週次報告書（型化・スナップショット・比較）

**やりたいこと**: ランダムに進捗を話す今の定例を、漏れのない型に。営業マン毎の週次報告書を作り、スナップショット保存＋過去参照＋2世代の並列比較。

**報告書テンプレ（要望の項目を実データにマッピング）**
| 報告項目 | データソース（既存） |
|---|---|
| 今月の目標／現在までの実績／月末見込み | `sales_targets`,`rep_targets` / 成約実績 / `weighted=金額×確度` |
| 先週の予定と実績と差分＋コメント | 前スナップショットの「来週予定」vs 今週実績 |

| 1ヶ月先までの想定工数・商談数・ステージ別顧客状況 | 予定商談数・工数見積 / ヨミ別集計 |
| 担当顧客・商談リスト＋優先度・ヨミ・自分の予測 | `opportunities`（ヨミ/確度/見込月/見込額）＋ **予測入力** |

**予測（自分の見立て）の入力＋AI補助**: 各案件に「成約タイミング(何月)／売上額／あと何回商談が必要か」を営業が入力。**AIが過去パターンから推定値を提示**し、営業はそれを調整（型B1の学習と連動）。

**スナップショット & 比較（既存 `xray_snapshots` の型を踏襲）**
- 週報を確定すると `weekly_report_snapshots(payload jsonb)` に **その週の全数値・コメントを丸ごと保存**。過去はいつでも同じ見た目で再現。
- **比較ビュー**: 2つのスナップショット（例: 今週 vs 先週、今週 vs 4週前）を左右に並べ、差分（増減・新規/消えた案件・コメント変化）をハイライト。
- 既存 `xray-snapshot` cron（15:30）と同じ枠で **週次の自動スナップショット** も可能（月曜朝の会議前に前週分を確定）。

**AIによる週報下書き**: 数字と活動から「先週の実績・差分コメント」の **叩き台をAIが自動作成** → 営業は確認・修正だけ。定例の準備時間を大幅圧縮。

**定例会アジェンダ自動生成**: 全員の週報スナップショットを束ね、WO-07 6.6を発展させた **「今週の会議アジェンダ」**（要確認案件・支援要請・遅延・好調）を自動生成。ランダム報告を型化。

**実現手段**: `xray_snapshots` パターン（既存）、既存の予測/ヨミ/目標データ、AI下書き。
**実現性**: ◎。スナップショット・比較・型化は既存基盤の直系で、確実性が高い。

**データモデル（新規）**: `weekly_report_snapshots(id, tenant_id, owner_user_id, week_start date, payload jsonb, comment_json jsonb, status('draft'|'finalized'), created_at)`

## 7. 夜間バッチ実行基盤 —「Claude Code方式（方針A）」で従量課金ゼロ

**確定方針（ユーザー決定・2026-07-12）**: 当面、夜間バッチのAI生成は **Anthropic API（従量課金）を使わず、Claude Code自身をスケジュール実行**して行う。消費は **Claudeサブスクの枠内**。就寝中の時間帯に走らせ、**5時間の利用枠を有効活用**する。将来、即時性が必要な機能だけ API従量方式（方針B）へ切り替える。

### 7.1 実行アーキテクチャ
```
[夜間トリガ] Claude Code Remote の Routine(cron) が毎晩セッションを起動
    │  例: 毎日 02:00 JST に fresh session を発火（create_new_session_on_fire）
    ▼
[Claude Code セッション]（消費 = サブスク枠）
    ├─ Supabase MCP: 対象を抽出
    │     ・翌日アポあり案件（ブリーフ対象 B2）
    │     ・当日 議事録テキスト有り＆未要約の商談（議事録対象 B3）
    │     ・週の締め（週報スナップショット B6）
    ├─ 生成: 型(B1)/ナレッジ(B7)を参照し、要約・ブリーフ・お礼下書き・NA候補を作成
    ├─ Supabase MCP: 生成物を status='draft' で書き戻す
    ├─ Gmail MCP: お礼/資料送付を「下書き」保存（送信しない）
    └─ Slack/通知: 「今朝の確認キュー N件」を担当へ
    ▼
[翌朝] 営業はアプリの確認画面で下書きを見て、修正 → 確定 / 手動送信
```

- **スケジューラ**: この環境の Routine（cron トリガ）。`create_new_session_on_fire=true` で毎晩クリーンなセッションを起動し、標準化したプロンプト（runbook）を渡す。Vercel Cron は使わない（Vercel経由でAPIを呼ぶと方針B＝従量課金になるため）。
- **バッチのロジックは「プロンプト/runbook」に置く**: 各夜間ジョブは「何を読み・何を生成し・どこへ書くか」を明文化した手順書として保存（Skill化 or ワークフロー化）。アプリ側コードにAI呼び出しを持たせない。
- **書き戻し**: Supabase MCP（`execute_sql` 等）で下書きテーブルへ直接。すべて `status='draft'`。

### 7.2 ガードレール（方針Aでも維持）
1. **対象を絞る**: 明確なトリガのある対象のみ（翌日アポ／当日議事録／週締め）。全件生成しない＝枠の節約。
2. **必ず人の関所**: 生成物は全て下書き。送信・確定・タスク化・案件更新は人のワンクリック。**Claude Codeが自動で送信・確定しない**。特にメール送信は手動（要望どおり）。
3. **冪等性**: 処理済みは印を付ける（`ai_summary_at`・briefingの `status` 等）。再実行で二重生成しない。
4. **利用枠の管理**: 1回の実行で処理する件数に上限を設け、超過分は翌晩へ繰り越し。枠に近づいたら中断して残件を記録。
5. **失敗に強く**: 1件失敗しても他は続行。生成漏れは翌朝の通知でわかる。
6. **運用ログ**: `batch_runs`（実行日時/対象種別/件数/成功・失敗）を記録。※APIのトークン課金監査 `ai_runs` は方針Aでは不要（方針Bへ切替時に有効化）。

### 7.3 方針A ↔ 方針B の切り替え設計（重要）
- アプリ側は **「下書きテーブル＋確認UI」までを持ち、AIの“書き手”を差し替え可能**にしておく。
  - 方針A: Claude Codeバッチが下書きを書く（従量ゼロ・非同期・夜間）。
  - 方針B: 即時性が要る機能だけ、アプリの Server Action → Anthropic API で **同じ下書きテーブル**に書く。
- こうしておけば、**UIとデータ構造を変えずに、機能単位で A→B へ昇格**できる（例:「議事録要約だけ即時ボタン化」）。既存 `generateMeetingSummaryAction` はBの雛形として温存。

### 7.4 方針Aの制約（認識しておくこと）
- **サブスクの利用上限に従う**（5時間枠＋プランの週次上限）。処理量が枠に収まる範囲で対象を絞る（7.2-1,4）。就寝中の実行で日中の対話利用と枠を食い合わないようにする。
- **常駐バックエンドではなくエージェント実行**。ハード化された本番サービスより運用は緩い＝社内自動化ツールとしての位置づけ。
- **Routine/環境が生きている必要**がある。停止に気づけるよう、実行結果を毎朝通知（無風でも「N件処理」を出す）。

## 10. 意思決定が必要な論点（次に決めたいこと）

1. **【決定済】AI実行は方針A（Claude Code方式・従量ゼロ）**（§7）。残る確認事項は (a) 実行時刻（就寝中の何時か）、(b) サブスクのプラン/枠が想定件数に足りるか、(c) 日中の対話利用と枠を食い合わないための上限。即時性が要る機能が出たら、その機能だけ方針Bへ昇格（§7.3）。
2. **メール運用**: 下書きは Gmail（`create_draft`）で確定。送信は **手動** で合意でよいか（要望どおり）。
3. **議事録の主入力**: tl;dv を正とするか、録音文字起こし/手メモとの優先順位。
4. **型づくりの初期投入**: 橋本インタビューを **どの形式（tl;dv録画/口述メモ/Q&A記入）** で行うか。最初の3〜5業種を決める。
5. **マーケの外部連携**: Web検索API・画像生成・公開先（WordPress/レンタルサーバー）を **今スコープに入れるか**、当面 ⑤ドラフトまで自動＋手動公開にするか。
6. **着手順**: 提案ロードマップ（WO-10→11→12 先行）で合意か、別の優先度があるか。
7. **予測入力の必須化**: 週報の「成約時期・売上額・残商談回数」を必須にするか（漏れ防止 vs 入力負荷）。

## 付録: 準拠する既存原則（踏襲）
- **加算的スキーマ**（既存テーブル/RLSを壊さない・列追加/付随テーブル）。
- 重い集計・夜間RPCは **SECURITY DEFINER + 明示テナント + `search_path`固定 + authenticated/CRON限定**。
- 破壊的/管理操作は `can_edit_role()` ガード。CronはCRON_SECRET認可＋service roleは `deleted_at` 明示除外。
- AIは **人の関所を必ず通す**。誤送信・誤情報を構造で封じる。
- AI実行は **方針A（Claude Code方式・従量ゼロ）を既定**とし、即時性が要る機能のみ方針B（API従量）へ機能単位で昇格（§7）。
- ブランチ運用・機微情報の非コミットは現行ルールを継続。
