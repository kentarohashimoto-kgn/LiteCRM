# freee 月末振込処理の効率化：取引先「振込先口座」インポート（2026-07）

> **目的**: 毎月の振込処理を freee の「一括振込ファイル（全銀フォーマット）」で自動化する。
> そのために取引先マスタへ振込先口座情報を登録する必要があるが、現状ほぼ全件が「口座未設定」。
> **本フェーズ**: 手元の請求書（PDF/画像）から口座情報を抽出し、freee 取引先インポート用CSVを生成する。
> **前提**: 最終的なインポート操作は人間が行う。成果物は「レビュー可能なCSV」と「要確認リスト」の2点。

実装: `tools/freee_transfer/`（Python・標準ライブラリ中心）

## 2. なぜ「実装を先に済ませる」のが正しいか

このタスクの失敗モードは処理が遅いことではなく、**間違った口座番号がCSVに載ること**である。
1文字の誤りがそのまま誤送金になる。

誤りの混入経路は、実データが届いてから慌てて書くコードにこそ生まれる。
逆に言えば、**誤送金に直結するロジック（カナ正規化・バリデーション・名寄せ）は
実データを1件も見なくても完全に検証できる**。だから先に作り、先にテストした。

現在 82 件のテストが通っている（`python -m unittest discover -s tests -t .`）。

## 3. 「推測で埋めない」をコードで担保する3つの仕掛け

指示書 §1-1 の原則は、レビュー時の心がけではなく実装の制約として落とし込んだ。

### 3-1. 自動抽出は `confidence` を `high` にしない

`extract.py`（正規表現ベース）が付けられる確度の上限は `medium`。
`validate.py` は必須項目に `high` を要求する。

結果として、**原本を目視した人間/エージェントが `work/extracted.json` を
`high` に更新しない限り、値はCSVへ到達しない**。
自動抽出はあくまで「下書き」であり、そのまま成果物にはならない。

### 3-2. 読めなかった文字は落とさず残す

`kana.normalize_kana()` は全銀フォーマットで使えない文字（漢字・中点など）を削除しない。
`invalid_chars` として報告し、その行は要確認へ回る。

黙って落とすと「それらしいが誤った名義」がCSVに載る。これが最も危険な失敗。
特に **漢字社名からカナを生成することは一切しない**（読み方の誤りは振込不能に直結する）。

### 3-3. 類似名は自動で紐付けない

`match.py` が `confirmed` にするのは正規化後の完全一致のみ。
`（株）`と`株式会社`、スペースの有無といった表記揺れは吸収するが、
**部分一致は必ず「要確認」として人間へ返す**。

実装中に見つけた穴を1つ潰してある。
「既存商事」と「既存商事ホールディングス」のような**包含関係は文字列類似度が低く出る**ため、
閾値判定だけでは「新規取引先」に落ちてしまう。これは取り違えが最も起きやすいパターンなので、
包含関係を別途検出して必ず候補に出すようにした。

## 4. STEP 1 を飛ばさない仕掛け

CSVの列名は **エクスポート実物のヘッダー行が唯一の正解**であり、指示書に書かれた列名例は参考にすぎない。

- `build.py` は `work/header.txt`（= エクスポート実物）からしか列名を取らず、列名を1つも生成しない
- `step1` は列の対応表を `work/column_map.json` へ出力する。人間が確認して
  `"confirmed": true` にするまで `build` は動かない
- 口座種別が「普通」なのか「1」なのか等は、**freee 側の既存行から実際に観測して**
  `work/schema_notes.md` に記録する

freee 側に口座登録済みの行が0件だと、この記法を実物から学べない。
その場合は警告を出し、**freee で1件だけ手入力して再エクスポートし STEP 1 をやり直す**よう促す。

## 5. パイプライン

| STEP | コマンド | 出力 |
|---|---|---|
| 0 | `preflight` | 入力3点の存在確認。足りなければここで停止 |
| 1 | `step1` | `work/header.txt` / `column_map.json` / `schema_notes.md` |
| 2 | `step2` | `work/extracted.json` / `work/pages/*.png`（スキャンページ） |
| 3 | `step3` | `work/matching.md` |
| 5-6 | `build` | `output/freee_import.csv` / `review.md` / `summary.md` |

STEP 2 と 3 のあとには、必ず人間（またはエージェント）の確認作業が入る。
`step2` は既存の `extracted.json` を上書きしない（`--force` が必要）。
目視確認済みの内容を、再実行で消さないための保護。

### バリデーション（STEP 5）

全件チェックし、1件でも引っかかれば要確認扱いにする。

- 必須項目（金融機関名・支店名・口座種別・口座番号・口座名義カナ）の欠損
- 口座番号が数字のみか
- 口座名義カナが30文字以内か（PayPay銀行 WEB総振の制限。**濁点・半濁点も1文字**）
- 口座名義カナに全銀フォーマットで使用不可の文字が含まれていないか
- 金融機関コード4桁 / 支店コード3桁（値がある場合のみ）
- 同一取引先の重複
- 抽出件数と入力ファイル数の整合

## 6. 実装上の判断

- **pandas を使わない**。`read_csv` の dtype 推論で口座番号の先頭ゼロが消える事故を避けるため、
  CSVの読み書きは標準 `csv` モジュールで文字列のまま扱う
- 出力CSVの文字コードはエクスポート実物に合わせる（freee は Shift_JIS のことがある）。
  判定は推測ではなく実際にデコードして確認する
- `input/` `work/` `output/` は `.gitignore` 済み。**口座情報・請求書は絶対にコミットしない**
- 中間ファイルは `work/` に残す（デバッグと検算のため）

### 保留にした判断

口座名義の中点（`・`、外国人名などで使われる）は全銀フォーマットの使用可能文字に含まれない。
半角スペースや `.` への置換が実務上よく行われるが、指示書の変換ルールに記載がないため
**自動変換せず要確認へ回す**。運用方針が決まればルールに追加する。

## 7. 次フェーズ：振込依頼人コードの後処理

freee は振込依頼人コード（委託者コード）の入力を要求するが、PayPay銀行の WEB総振では不要。
任意の10桁を入れて全銀ファイルを出力し、**出力ファイル側の該当箇所をスペースに置換する**
後処理が必要になる見込み。この変換スクリプトは別タスクで作成する。

全体の流れ：

1. 本CSVを freee 取引先マスタへインポート（人間）
2. freee 支払管理レポートで支払対象を選択
3. 「一括振込ファイル」を全銀フォーマットで出力
4. **振込依頼人コード欄をスペースへ置換**（← 次フェーズ）
5. PayPay銀行 WEB総振へアップロードして振込実行
