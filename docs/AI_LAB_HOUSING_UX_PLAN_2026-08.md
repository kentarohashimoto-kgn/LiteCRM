> **位置づけ**: 実装前の設計検討メモ。「建築・住宅・不動産業界 AI活用事例・活用アイデア集」の★項目を、

## 1. 結論（先に3行）

1. アイデア集の★は **7つのUI原型** に集約できる。うち **半分は「1問1答のチャット」では成立しない**（結果が表であり、人が潰していく作業台になるため）。
2. 既存の「スライド作成」が **チャットでない専用画面の先例** として完成している（構成案 → 1件ずつ生成 → 統合 → 成果物DL）。この実行モデルは **突合チェック・一括仕分け・バリエーション生成にそのまま流用できる**。
3. 最も効果／工数比が高いのは **①ランチャー画面 ②住宅業界プリセットパック** で、どちらもほぼ実装ゼロ。次に **ロープレ道場**（軽い・事例で語れる）、本命は **突合チェック**。

## 2. 現状の AI Lab で何ができているか（設計の出発点）

| 資産 | 内容 | 転用先 |
|---|---|---|
| チャット（`/lab/{slug}/chat`） | マルチターン・ストリーミング・モデル切替・添付（PDF/画像/テキスト 15MB×5件）・ファイル生成（xlsx/docx/pptx/PDF） | 原型②④⑤の土台 |
| スライド作成（`/lab/{slug}/slides`） | **3段構成**（構成案づくり → 1枚ずつ画像生成 → PPTX統合）。1枚1リクエストで関数300秒上限を回避、失敗を局所化 | **原型①③⑥の実行モデルそのもの** |
| プリセット＋アセット | 管理者が仕込むシステムプロンプト＋参照資料（24,000字まで注入）。受講者には名前と説明だけ見える（AL-504） | 原型②、業界パック |
| 添付基盤 | `ai_lab_attachments` + Storage + 署名URL。履歴全体18MB予算で古い添付から落とす | 全原型で共通 |
| 費用制御 | 月間トークン予算 / 1分あたり送信上限 / 画質High 1日10枚 / `is_unlimited` 免除 | 一括処理系の暴走防止にそのまま効く |
| 会社別分離 | Basic認証 + 個別ログイン + RLS。会社ごとに利用可能モデル・既定モデル | 変更不要 |

**重要な制約（設計を縛るもの）**

- サーバレス関数の実行時間 **300秒**。10件以上のバッチ処理は「1件1リクエストをブラウザから順に叩く」しかない（スライドと同じ）。
- 添付は API がステートレスなため**毎回送り直し**。履歴18MB予算で古い添付から落ちる（AL-211）。図面PDFのような大物を扱う画面では、この予算設計を画面ごとに見直す必要がある。
- 現行の CSV 取込基盤（`decodeFileText` / `uniquifyHeaders` / `parseDelimited`）は **Shift_JIS フォールバック込み**。現場のExcel事情にそのまま効くので、表を扱う原型では必ず再利用する。

## 3. アイデア集 → UI原型のマッピング

| 原型 | 該当する★アイデア | チャットで成立するか |
|---|---|---|
| **① 突合チェック（ワークシート型）** | 議事録×図面の反映漏れ／部材リスト×見積明細／契約書×社内チェックリスト／点検データの抜け漏れ | **不可**。結果は表であり、行ごとに人が潰す作業が本体 |
| **② 資料に聞く（根拠つきQ&A）** | 商品仕様ボット／設計標準・法規解釈ボット／単価問い合わせボット／メンテ・保証基準ボット／就業規則ボット | 可能だが**出典表示と原文参照ペインが要る**。5領域の★が集中する最大公約数 |
| **③ 一括仕分け表** | 不具合問い合わせの分類・集計／CSアンケート自由記述の分類・ポジネガ／全拠点顧客データの横断分析 | **不可**。数百行をチャットに貼れない |
| **④ ロープレ道場** | 商談ロープレ（大東建託「AI課長」事例） | チャットUIは使うが、**設定と採点**が別に要る |
| **⑤ ヒアリングシート化** | 商談録音→ヒアリングシート／施主要望の構造化（絶対条件・希望・トレードオフ） | **不向き**。出力は定型フォームであるべき |
| **⑥ バリエーション・グリッド** | ペルソナ別コピー出し分け／暮らしのシーン画像／見学会バナー／手描き図面→パースのバリエーション即出し | 可能だが1案ずつになる。**並べて見比べる**のが価値 |
| **⑦ 現場モード（モバイル）** | 現場写真＋メモ→工事報告書・施主向け進捗報告／協力業者向け通知・掲示物 | 機能は可能。**PCのチャット画面では現場で使えない** |
| （既存でカバー） | 月次数値→経営会議スライド／プラン提案プレゼンの構成→スライド | スライド作成機能で概ね対応済み |

## 4. 各原型の画面設計案

### ① 突合チェック（クロスチェック） — 本命

**なぜチャットではダメか**: 「反映漏れを教えて」に長文で返されても、次に何をするかが残らない。実務（是正指示・検査・施工図チェック）は **項目を一行ずつ潰す作業** であり、UIも作業台でなければならない。

**画面**

```
Step 1  チェックの型を選ぶ
  ・議事録 × 図面（打合せ内容の反映漏れ）
  ・部材リスト × 見積明細（数量齟齬・発注漏れ）
  ・工事請負契約書 × 社内チェックリスト（不備候補）
  ・点検記録 × 点検項目表（記入漏れ）
  ※ 型 = 管理者が仕込むプリセットの拡張。基準側（A）を会社アセットとして固定できる

Step 2  A（基準・チェックリスト）と B（対象資料）を投入
        A は「社内基準を選ぶだけ」で済むケースが多い

Step 3  実行 ─ チェック項目ごとに1リクエスト
        進捗「7/24 件」。1件失敗しても止めない・そこだけ再実行（スライドと同じ思想）

Step 4  結果ワークシート
 ┌───┬──────────────┬────────┬──────────────┬──────────┬──────┐
 │ # │ チェック項目        │ 判定    │ 根拠（A該当）  │ 対象での確認先 │ 対応  │
 ├───┼──────────────┼────────┼──────────────┼──────────┼──────┤
 │ 1 │ 玄関土間の仕上げ変更  │ 不一致  │ 議事録 p.2 3行目│ 図面 A-03    │ [済]  │
 │ 2 │ 造作カウンター寸法   │ 記載なし│ 議事録 p.3     │ —          │ [保留]│
 └───┴──────────────┴────────┴──────────────┴──────────┴──────┘
   判定 = 一致 / 不一致 / 記載なし / 要確認
   行クリック → 右ペインに原文を表示（AIの主張を必ず原文で確認できる）
   「対応」列は人が入れる（済／保留／対象外＋メモ）

Step 5  Excel / PDF 出力（既存のファイル生成ツールへ接続）
```

**データモデル（スライドとほぼ同型）**

- `ai_lab_check_runs`（deck 相当）: 型・A/B の添付参照・status(draft/running/ready/failed)
- `ai_lab_check_items`（slide_items 相当）: position・チェック項目・判定・根拠・所見・人の対応ステータス

→ **`slides-db.ts` / `slides.ts` / render ルートの構造を写せる**。新規性はUI（表 + 原文ペイン）に集中する。

**研修でのデモ映え**: 議事録と図面PDFを2枚放り込んで「反映漏れ3件」が表で出る。ハンズオンの山場になる。

### ② 資料に聞く（根拠つきQ&A）

**現行チャット＋プリセットとの差分**

1. **受講者が自分で資料束（ナレッジ）を作れる。** 現行は管理者だけがアセットを仕込む設計（AL-504）。研修としては「自部署のカタログ・規程を自分で入れて聞く」体験のほうが刺さる。→ 権限設計の変更を伴う（§6）。
2. **回答に出典チップを必ず付ける。** `[仕様書2026.pdf p.14]` をクリック → 右ペインに該当箇所。単価・法規・寸法は出典なしに書かせない。
3. **「資料に無ければ答えない」モード。** ハルシネーション対策を機能として持つ。該当記載なし → 「記載がありません」と返し、推測は別枠に隔離。
4. **入口の質問サジェスト。** 資料を入れた直後に「この資料からよく聞かれること」を3件自動提示。**何を聞けばいいか分からない問題**への回答。

**設計判断（§6-1）**: RAG（`document_chunks`／0169の基盤）を入れるか。
研修で扱う数十MB規模なら **全文注入＋出典明記の指示** で足りる（注入上限24,000字の引き上げで対応）。仕様書数百ページを常用するなら既存RAG基盤の転用が要る。v1は前者、拡張余地として後者を残す。

### ③ 一括仕分け表

**画面**: CSV/Excel をアップ → 表プレビュー → **「AI列を追加」**

```
[ 追加する列 ] 部位分類
[ 指示       ] 不具合内容から部位を1つ選ぶ
[ 出力形式   ] ● 選択肢（屋根/外壁/開口部/内装/設備/構造/その他）
               ○ 数値  ○ 自由文  ○ ポジネガ3段階
```

- 実行は **20行バッチ × N回**（1行1リクエストだと遅く高い、全件1回だと300秒に当たる）
- 集計タブ：クロス集計＋グラフ（部位×工程、月次推移）
- **「この集計から報告スライドを作る」→ 既存スライド機能へ受け渡し**。アイデア集の「経営報告スライド化」がここで繋がる
- 既存 `parseDelimited` / `decodeFileText` を再利用（Shift_JIS のCSVが普通に来る領域）

**適用**: 不具合問い合わせの傾向分析、CSアンケート、全拠点顧客データの重複・ステータス整理。

### ④ ロープレ道場 — 実装コスパ最良

**チャットUIを使うが1問1答ではない部分**

```
[開始前] シナリオを組む
  顧客タイプ : 一次取得30代 / 建替え60代 / 二世帯 / 相続・資産活用
  場面       : 初回来場 / プラン提案 / 資金計画 / 競合比較 / クロージング
  性格       : 素直 / 慎重 / 価格重視 / 他社推し
  難易度     : ★☆☆ 〜 ★★★

[会話中] 右ペインにヒアリング項目チェックリストがリアルタイムで埋まる
  ☑ 予算   ☑ 土地   ☐ 入居希望時期   ☑ 家族構成   ☐ 決裁者   ☐ 競合

     ↑ ここが1問1答チャットとの決定的な差。
       「聞けていないこと」が会話中に見えるので、練習が練習になる。

[終了後] 採点レポート

  改善点3件＋模範的な言い回し
```

**実装は軽い**（チャット＋シナリオのシステムプロンプト＋終了時の評価1リクエスト）。大東建託「AI課長」の公表事例があるため、提案の説得力も高い。**Phase 1 に置く理由**。

### ⑤ ヒアリングシート化

- 商談録音の文字起こし／メモ／議事録を投入 → **定型シートに自動充填**
- **空欄＝未ヒアリング項目**として明示し、「次回聞くこと」を自動生成
- 施主要望は4象限に構造化（絶対条件／希望／妥協可／トレードオフ）。**カードのドラッグで人が直せる**——AIの分類を最終決定にしない
- ④とチェックリスト思想が同じなので、コンポーネントを共通化する

---

### ⑥ バリエーション・グリッド

- 2軸を設定して n×m を一気に生成（ペルソナ×訴求軸／季節×時間帯／内装テイスト×家族構成）
- 1セル1リクエスト（スライドの実行モデルを流用）、画質・枚数の上限は既存 `limits.ts` がそのまま効く
- 気に入ったセルから「これを軸に派生」で次のグリッドへ
- 手描きゾーニング図を放り込んで**打合せ中に仕様違いを即出し**する使い方が、設計領域の★の核

---

### ⑦ 現場モード（モバイル）

- 写真を選ぶ → 一言メモ → 工事報告書／施主向け進捗報告のドラフト
- 大きいタップ領域、片手操作、電波の悪い現場での下書き保持
- 現行要件では**モバイル最適化は明示的に対象外**（§2.2「レスポンシブで閲覧可能なレベル」）。施工・アフター領域の★を活かすなら、ここは要件の見直し判断が要る（§6-4）

## 5. 横断で効く設計（住宅業界ならでは）

### 5-1. ランチャー画面 — 最優先・実装最小

現状 `/lab/{slug}` に入るといきなりチャットの空欄が出る。**住宅業界の受講者は「何を聞けばいいか」で止まる。**
入口を業務別カードグリッドに置き換える。

```
 集客・広報      営業         設計          積算・購買
 施工・現場      アフターCS   管理部門      経営・データ

  └ 各ブロックに3〜5枚のテンプレカード
     押すと適切なツールが起動する（チャット／突合／スライド／グリッド）
     例）「打合せ議事録と図面の反映漏れをチェック」→ 突合チェック
        「施工事例の紹介文を作る」→ チャット（プリセット適用済み）
```

### 5-2. 住宅業界プリセットパック — 実装ほぼゼロ・効果最大

現行は会社ごとに管理者が手作りする。住宅業界向けに **完成プリセット30本前後** をテンプレート集として持ち、会社作成時にワンクリックで流し込めるようにする。研修準備の工数が最も削れる打ち手で、コードはコピー機能だけ。

### 5-3. 数値・法規のガード

寸法・単価・法規・補助金は**間違えると実害が出る領域**。二重で守る。

- システムプロンプト側: 出典のない数値は書かせない／単位を必ず併記
- UI側: 回答中の数値・法令名に⚠️バッジ、「原典を確認してください」を回答の外枠に固定表示

### 5-4. 個人情報マスキング支援

施主名・住所・電話番号を送信前に検出してハイライトし、ワンクリックで伏字化。
アイデア集の「注意点セット」を**説明ではなく機能に落とす**ことになり、提案上の差別化になる。

### 5-5. 図面PDFの扱い

1件15MBの制約に当たりやすい。ページ選択UI（必要な図面だけ渡す）と、図面は画像化して渡す経路を用意する。

### 5-6. 業界用語・単位の前提

坪／㎡、尺モジュール、UA値・C値、長期優良、フラット35 などの前提を**会社設定レベル**のガードレールに持たせる（プリセットごとに書かせない）。

### 5-7. 成果物は必ず持ち帰れる形に

xlsx/docx/pptx/PDF の生成は実装済み。**突合結果・仕分け表・ロープレ採点も全部そこへ接続する。**
「画面で見て終わり」にしないことが、研修後の社内展開に効く。

## 7. 要決定事項（着手前に潰す）

1. **RAG の要否ライン** — 全文注入で足りる資料規模か、`document_chunks`（0169）の転用まで踏み込むか。②の設計が分岐する。
2. **受講者が資料束を作れるようにするか** — 現行はアセット管理が管理者専権かつ中身は受講者非表示（AL-504）。開放するなら権限・容量・保持期間の設計変更が要る。
3. **一括処理のコスト上限** — ①③⑥はリクエスト数が跳ねる。研修中の同時接続（1社20名想定？）× バッチで月間トークン予算をどう積むか。既存 `limits.ts` に「1ジョブあたりの上限」の概念を足す必要がある。
4. **モバイル対応の範囲** — 要件 §2.2 で対象外としている前提を変えるか。⑦の可否がこれで決まる。
5. **成果物の保持期間** — 突合結果・仕分け表は業務データに近づく。研修用の一時データとして扱うか、契約期間中は残すか（現行の「契約終了後1年」方針との整合）。
6. **どの原型から顧客に見せるか** — サーラ住宅様の事前課題との突き合わせ。★の重心が「設計・積算・アフター」に寄っているなら Phase 2（突合）を前倒しする判断もある。
