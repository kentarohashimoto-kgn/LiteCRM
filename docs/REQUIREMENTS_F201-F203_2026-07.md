# タスク管理 強化要件書（F-201 / F-202 / F-203）2026-07

> **目的**: Asana等からの乗り換え時に最も指摘される欠落機能を埋め、タスクモジュール（0096「Asana型」刷新）を実運用で完結できる水準にする。
> **対象**:
> | ID | 機能 | 現状 | 規模 | 背景 |
> |---|---|---|---|---|
> | F-201 | ガントチャート・依存関係・マイルストーン | ✕ | 大(L) | 乗り換え時に最も聞かれる欠落 |
> | F-202 | サブタスク・繰り返しタスク | ✕ | 中(M) | 定型業務・分解運用に必須 |
> | F-203 | タスクコメント・@メンション | ✕ | 小〜中(S-M) | 指示・引継ぎがSlackに散逸する |
>
> **前提となる既存実装**（本要件はすべてこの資産の上に構築する）:
> - タスク基盤: `task_portfolios` → `task_projects` → `task_sections` → `tasks`（0096）。ビューはリスト/ボード/カレンダー（`task_projects.default_view`）。`tasks` は `start_date` / `due_date`(null可) / `sort_order` / `labels`(0103) / `color`・`priority`(0129) / `url`(0134) / `origin`(next_action同期 0135) を保有
> - 参照権限: プロジェクトは「割当メンバー＋管理者＋作成者/オーナー」のみ参照（`task_project_members`, 0103）
> - コメント前例: `opportunity_comments`(0066) / `lead_comments`(0100) — body + `mentions uuid[]` + RLS(削除は本人or管理者)
> - 通知基盤: `notifications`(0071, kind=mention等) ＋ アプリ内ベル ＋ Slack通知（`src/server/actions/comments.ts` の `addOppCommentAction` が実装パターン）
> - 画面: `/app/tasks`(マイタスク) / `/app/tasks/projects/[id]` / portfolios / goals。ビュー実装は `src/components/tasks/task-views.tsx`

## F-201 ガントチャート（タイムライン）・依存関係・マイルストーン

### 1. 目的
プロジェクトの「いつ・何が・どの順で」を1画面で俯瞰し、日程調整をドラッグで完結させる。展示会準備・助成金対応（BO-1）・採用案件など、期日連鎖のある業務の計画をCRM内で完結させる。

### 2. 機能要件

#### 2.1 タイムラインビュー（ガント）
- **FR-201-01**: プロジェクト詳細（`/app/tasks/projects/[id]`）に第4のビュー「タイムライン」を追加する。`task_projects.default_view` の許容値に `timeline` を追加。
- **FR-201-02**: 縦軸はセクション（`task_sections`）ごとにグルーピングした行（リストビューと同じ並び順）、横軸は日付。タスクは `start_date`〜`due_date` の横バーで描画する。
  - `start_date` が無い場合は `due_date` 当日の1日バーとして表示
  - 両方無いタスクは左ペイン（行リスト）にのみ表示し、バー領域に「日程未設定」プレースホルダを出す。プレースホルダのクリック→当該位置の日付で設定できる
- **FR-201-03**: ズーム切替: **日 / 週 / 月 / 四半期**。既定は週。「今日」への即時ジャンプボタンと今日を示す縦線を常時表示する。
- **FR-201-04**: バーの**ドラッグで期間移動**、**両端ドラッグで開始日/期日の変更**ができる。変更は既存のタスク更新アクション（`src/server/actions/tasks.ts`）を通し、楽観更新＋失敗時ロールバックとする。
- **FR-201-05**: バー上に タイトル・担当者アバター・優先度/ラベル色（`tasks.color`→無ければプロジェクト色）を表示。完了タスク（status=done）は淡色＋打ち消しで残す（非表示トグルあり）。
- **FR-201-06**: 既存のフィルタ（担当者・ラベル）とマイタスク/チーム切替をタイムラインでも共通で効かせる。

#### 2.2 依存関係
- **FR-201-10**: タスク間に「先行→後続」の依存を設定できる。v1の依存タイプは **FS（先行の完了後に後続を開始）のみ**。1タスクに複数の先行/後続を許容する。
- **FR-201-11**: 設定手段は2つ。(a) タスク詳細パネルの「依存関係」欄からタスク検索で追加/削除、(b) タイムライン上でバー端点から別バーへドラッグして接続。
- **FR-201-12**: タイムライン上で依存を矢印（コネクタ線）として描画する。
- **FR-201-13**: **循環依存はサーバー側で検出して拒否**する（A→B→C→A を禁止。挿入時に到達可能性チェック）。エラー文言は「循環する依存関係は設定できません」。
- **FR-201-14**: **日程矛盾の警告（v1は警告のみ、自動シフトなし）**: 後続タスクの開始日（無ければ期日）が先行タスクの期日より前の場合、タイムライン上で当該コネクタと後続バーを警告色にし、タスク詳細にも警告バッジを表示する。
- **FR-201-15**: 先行タスクが未完了のまま後続タスクを完了しようとした場合、確認ダイアログ（「先行タスクが未完了です。完了しますか？」）を出す（ブロックはしない）。
- **FR-201-16**: タスク削除時は関連する依存行も削除（FK cascade）。プロジェクト間をまたぐ依存は v1 では**同一プロジェクト内のみ**に制限する。

#### 2.3 マイルストーン
- **FR-201-20**: タスクを「マイルストーン」として作成/変換できる（`tasks.is_milestone`）。マイルストーンは `due_date` 必須・`start_date` なしの一点イベント。
- **FR-201-21**: タイムラインではバーではなく**ダイヤ（◆）記号**で描画。カレンダー/リスト/ボードでも◆アイコンを付す。
- **FR-201-22**: プロジェクトヘッダーに「次のマイルストーン（名称＋残日数）」を表示する。超過時は赤表示。
- **FR-201-23**: マイルストーンも通常タスクと同様に担当者・依存関係・コメント（F-203）を持てる。期限リマインドは既存のタスク期限通知（毎朝ダイジェスト）に相乗りする。

### 3. データモデル（マイグレーション案: 0139）
```sql
-- 依存関係
create table public.task_dependencies (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid not null references tenants(id) on delete cascade,
  predecessor_task_id uuid not null references tasks(id) on delete cascade,
  successor_task_id uuid not null references tasks(id) on delete cascade,
  dep_type text not null default 'fs',   -- v1はfsのみ。将来: ss/ff/sf
  lag_days integer not null default 0,   -- v1はUI非公開（0固定）
  created_by uuid references auth.users(id),
  created_at timestamptz not null default now(),
  unique (predecessor_task_id, successor_task_id),
  check (predecessor_task_id <> successor_task_id)
);
-- マイルストーン
alter table public.tasks add column if not exists is_milestone boolean not null default false;
-- default_view の許容値に 'timeline' を追加（アプリ側定数）
```
RLS はタスク系の既存方針（tenant境界＋`can_edit_role`）を踏襲。循環検出は insert 用の RPC（再帰CTEで到達判定）で行う。

### 4. 非機能・受け入れ基準
- **NFR**: 1プロジェクト500タスク＋依存200本で初回描画2秒以内。取得は表示プロジェクト単位（全件取得しない）。モバイルは横スクロールで閲覧可能（編集はデスクトップ優先）。
- **AC-201**:
  1. タイムラインでバーをドラッグすると start/due が保存され、リロード後も反映されている
  2. A→B の依存があるとき B→A を追加するとエラーになる
  3. 先行の期日より前に後続の開始日を設定すると警告表示になる（保存自体は可能）
  4. マイルストーンが◆で表示され、プロジェクトヘッダーに次マイルストーンが出る
  5. プロジェクト参照権限のないユーザーにはタイムラインも見えない（既存RLS準拠）

### 5. スコープ外（v1）
自動リスケジュール（依存先の日程を連動シフト）／クリティカルパス計算／リソース稼働管理／FS以外の依存タイプUI／ポートフォリオ横断ガント／ベースライン比較。→ 需要を見て v2。

## F-202 サブタスク・繰り返しタスク

### A. サブタスク

#### 1. 機能要件
- **FR-202-01**: タスクの下に子タスク（サブタスク）を作成できる。**階層は1段のみ**（サブタスクの下にさらに作らせない。UI・サーバー両方で制止）。
- **FR-202-02**: サブタスクは通常タスクと同じ属性（担当者・期日・優先度・ラベル・コメント）を持つ独立レコード。既定では親の `project_id` / `section_id` を継承する（変更可）。
- **FR-202-03**: タスク詳細パネルに「サブタスク」欄: チェックリスト形式で一覧・インライン追加（タイトル＋Enter）・完了チェック・並び替え（`sort_order`）・削除。
- **FR-202-04**: リスト/ボードのカードに **進捗バッジ「済n/全m」** を表示。ボード・リスト・カレンダーの最上位一覧にはサブタスクを既定で表示しない（トグル「サブタスクを表示」で展開。リストでは親の下にインデント表示）。
- **FR-202-05**: **マイタスクには自分が担当のサブタスクも表示**する（親が他人担当でも自分の作業として見える。親タイトルをパンくずで併記）。
- **FR-202-06**: 未完了サブタスクが残る親を完了しようとしたら確認ダイアログ（「未完了のサブタスクがn件あります」→ 完了を続行 / 子もまとめて完了 / キャンセル）。
- **FR-202-07**: 親タスク削除時はサブタスクも削除（FK cascade。確認ダイアログに件数を明示）。既存タスクを別タスクのサブタスクへ変換／サブタスクを独立タスクへ昇格できる。
- **FR-202-08**: タイムライン(F-201)では親の直下にインデント表示。依存関係はサブタスク単位でも設定可。

#### 2. データモデル（0140）
```sql
alter table public.tasks add column if not exists parent_task_id uuid references tasks(id) on delete cascade;
create index if not exists idx_tasks_parent on public.tasks(parent_task_id);
-- 1階層制約: parent_task_id を持つタスクを親に指定できない（trigger or RPCで検証）
```

### B. 繰り返しタスク

#### 1. 機能要件
- **FR-202-20**: タスクに繰り返しルールを設定できる。パターン:
  - **毎日**（間隔n日 / 平日のみ）
  - **毎週**（間隔n週＋曜日複数選択）
  - **毎月**（間隔nヶ月＋「d日」or「第n X曜日」or「月末」）
  - **毎年**（月＋日）
  - 終了条件: なし / 指定日まで / n回で終了
- **FR-202-21**: 生成方式は **Asana方式＝完了時生成**。繰り返しタスクを完了した瞬間に、次回日付で新しいタスクを1件生成する（cronでの事前一括生成はしない）。
  - 次回日付はルール上の次回。**期限超過後に完了した場合は「今日以降で最初のルール日」**とする（過去日タスクを量産しない）
  - `start_date` がある場合は start/due の間隔を保って両方シフト
- **FR-202-22**: 生成時のコピー範囲: タイトル・説明・担当者・プロジェクト/セクション・ラベル・優先度・色・URL・**サブタスク（全件を未完了状態で複製）**・繰り返しルール自体。コメント(F-203)と完了状態はコピーしない。
- **FR-202-23**: カード・詳細に繰り返しアイコン（🔁）とルールの日本語要約（例「毎週 月・木」）を表示。ルールの編集・解除は次回生成分から反映（生成済みタスクは遡って変更しない）。
- **FR-202-24**: 繰り返しの連鎖を追跡できるよう生成元タスクIDを記録する（削除時に「今後の繰り返しも停止するか」を選択可能に）。

#### 2. データモデル（0140 同梱）
```sql
alter table public.tasks add column if not exists recurrence jsonb;          -- ルール（null=繰り返しなし）
alter table public.tasks add column if not exists recurrence_source_id uuid references tasks(id) on delete set null;  -- 生成元
```
`recurrence` 例: `{"freq":"weekly","interval":1,"weekdays":[1,4],"ends":{"kind":"count","value":10,"done":3}}`。次回日付計算はサーバー側の純関数として実装し、**回帰テスト必須**（E-5方針: 月末・第5週・うるう年・超過完了のケースを含む）。

### 3. 受け入れ基準
- **AC-202**:
  1. サブタスク3件中1件完了で親カードに「済1/全3」と表示される
  2. サブタスクの下にサブタスクを作れない
  3. 「毎週月曜」のタスクを金曜に（超過状態で）完了すると、次の月曜のタスクが1件だけ生成される
  4. n回終了のルールが上限に達すると以後生成されない
  5. 繰り返しタスク完了時、サブタスクが未完了状態で次回タスクに複製されている

### 4. スコープ外（v1）
2階層以上のネスト／祝日スキップ・営業日補正／RRULE完全互換／繰り返しの事前スケジュール一覧表示。

## F-203 タスクコメント・@メンション

### 1. 目的
タスク上の指示・相談・引継ぎをタスク自体に残し、Slackへの散逸を防ぐ。既存の案件コメント（C-2, `opportunity_comments`）と完全に同じ操作感・通知動線にそろえる。

### 2. 機能要件
- **FR-203-01**: タスク詳細パネル下部にコメントスレッド（古→新、最新までスクロール）。プレーンテキスト＋改行。投稿は Cmd/Ctrl+Enter。
- **FR-203-02**: 本文中の `@` でテナント内メンバーのサジェスト（`profiles` の表示名/メール検索）。メンションは `mentions uuid[]` に保存（既存C-2と同形式、上限20名）。
- **FR-203-03**: 通知は `addOppCommentAction`（`src/server/actions/comments.ts`）のパターンを共通化して流用:
  - メンション相手へ **アプリ内ベル**（`notifications` kind=`mention`、title「◯◯さんがコメントであなたをメンション」、href=当該タスクを開くディープリンク）＋ **Slack**（設定時のみ。失敗しても投稿は成立）
  - メンションが無くても**タスク担当者（assigned_to）へは通知**する（投稿者本人は除外）
  - href は `/app/tasks/projects/[projectId]?task=[taskId]`（プロジェクト未所属タスクは `/app/tasks?task=[taskId]`）。遷移時に該当タスクの詳細パネルを自動で開く
- **FR-203-04**: 削除は本人または管理者(owner/admin)。v1では編集不可（C-2と同一ポリシー）。削除時は物理削除。
- **FR-203-05**: カード・リスト行にコメント数バッジ（💬n）を表示。
- **FR-203-06**: システムイベント（担当者変更・期日変更・完了）はv1ではコメント欄に混ぜない（B-1変更履歴の管轄）。
- **FR-203-07**: 権限: コメントの参照可否はタスク本体のRLSに従う（プロジェクト参照権限のないユーザーはコメントも見えない）。

### 3. データモデル（0141）
```sql
create table public.task_comments (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid not null references tenants(id) on delete cascade,
  task_id uuid not null references tasks(id) on delete cascade,
  author_user_id uuid not null references auth.users(id),
  body text not null,
  mentions uuid[] not null default '{}',
  created_at timestamptz not null default now()
);
create index idx_task_comments_task on public.task_comments(task_id, created_at desc);
-- RLS: select=tenant内（タスク参照可否はアプリ層＋タスクRLSで担保）/ insert=本人 / delete=本人or管理者（0066と同形）
```

### 4. 受け入れ基準
- **AC-203**:
  1. コメントで@メンションすると相手のベルとSlack（設定時）に通知が届き、通知クリックで該当タスクの詳細パネルが開く
  2. メンション無しコメントでも担当者に通知が届く（本人投稿時は届かない）
  3. 他人のコメントは削除できない（管理者は可能）
  4. プロジェクト参照権限のないユーザーにはコメントが見えない

## 実装順・工数の推奨

| 順 | 対象 | 理由 | 工数目安 |
|---|---|---|---|
| 1 | **F-203 コメント/メンション** | 既存C-2の移植で完結。通知資産をそのまま流用でき即効性が高い | S-M（2-3日） |
| 2 | **F-202 サブタスク → 繰り返し** | スキーマ小・UI中。繰り返しは次回日付計算のテストを厚く | M（4-6日） |
| 3 | **F-201 タイムライン/依存/マイルストーン** | 描画・ドラッグ操作の実装量が最大。F-202のサブタスク表示を含めて最後に | L（1.5-2週） |

マイグレーション番号は 0139（依存/マイルストーン）・0140（サブタスク/繰り返し）・0141（コメント）を想定（実装時点の最新に合わせて振り直し）。

## 実装前に確認したい未確定事項
1. **F-201**: 依存の日程矛盾は「警告のみ」でよいか、自動シフト（後続を押し出す）まで必要か → v1警告のみを推奨
2. **F-201**: ガントのタスク数規模感（1プロジェクト最大何件想定か。500件を性能目標に置いた）
3. **F-202**: 繰り返しの「完了時生成」方式でよいか（cron事前生成だと未来のタスクが一覧を圧迫するため非推奨）
4. **F-202**: 祝日・営業日補正の必要性（v1スコープ外とした）
5. **F-203**: コメント編集機能の要否（v1は削除のみ。C-2と同一ポリシー）
