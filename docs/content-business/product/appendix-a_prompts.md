# 付録A プロンプト実例集

実際の開発で使った指示を、場面別に整理した道具箱です。（　）内は自社の言葉に
差し替えてください。各プロンプトの末尾に「なぜこう書くか」を1行で添えています。
本文の該当章も併記しているので、背景を知りたいときはそちらへ。

> 使い方のコツ：コピペで使い始めて構いません。ただし3回使ったら、
> 自分の言葉に直してください。プロンプトは道具であり、道具は手に馴染ませるものです。

---

## 場面1：要件定義（第1章・第12章）

**A-1 要件を引き出させる壁打ち**
```text
あなたはBtoB営業の業務設計に詳しいコンサルタントです。
私は自社専用のCRM/SFAをAIコーディングで作ろうとしています。
これから自社の営業のやり方を口語で説明するので、質問で引き出しながら
「開発AIに渡す要件定義書」に整理してください。
必ず含める構成：1.変えたい仕事の場面 2.商談ステージとヨミ・確度の定義（数値まで）
3.利用者ロールと見えてよいデータ範囲 4.画面一覧（最小構成と後回し）
5.デザインの基準 6.今回は作らないことリスト
私の説明：（話し言葉でOK）
```
→ 書くより「質問に答える」方が速く、抜けが少ない。

**A-2 確度基準の表化**
```text
うちの営業の確度管理を表に整理するのを手伝ってください。口語で説明するので
「段階／呼び名／判定基準／受注確率の目安」の表に整え、人によって解釈が
割れそうな判定基準に印をつけてください。説明：（例：アポ取れたら30%…）
```
→ 「割れそうな箇所に印」で、曖昧さをAIに検出させる。

## 場面2：初日の構築（第2章・第13章）

**A-3 最初の一式（デモモード）**
```text
添付の要件定義書に基づいて、CRM/SFAの最初のバージョンを実装してください。
条件：
- まずデータベース未接続でも全画面が動く「デモモード」として作る
  （現実的なサンプルデータで画面と流れを確認できる状態）
- ただし設計は本番前提：マルチテナント構造・ロール別アクセス制御を最初から想定
- 自社固有のマスタ（商材・目標値）はコードに直書きせず設定データとして分離
- 要件定義書の「作らないことリスト」の機能は実装しない
```
→ 「触れる完成予想図」を最初に作ると、以後の指示精度が跳ね上がる。

**A-4 本番化（実認証・RLS）**
```text
デモモードを本物に切り替えてください。
- 認証：メール＋パスワードの実ログイン。未ログインでは業務画面に入れない
- データ：入力内容がデータベースに永続保存される
- 権限：ロール別の閲覧範囲を、画面の出し分けではなくデータベースのRLSで強制する
- 完了後、ロールごとの検証手順（誰でログインし、何が見え、何が見えないはずか）を
  表で出力。私がその表のとおり実測します
```
→ 検証手順をAIに出させ、実測は自分がやる。作った本人に採点させない。

## 場面3：修正ラリー・差し戻し（第13章）

**A-5 操作可能な修正指示（基本形）**
```text
（画面名）を直します。変更は以下の3点だけ。他は変えないでください。
1.（数字・位置・順序で指定） 2.（同） 3.（同）
```
→ 「見にくい」ではなく、数字・位置・順序。感想は指示にならない。

**A-6 ズレたとき（差分の言語化）**
```text
意図と違います。私が欲しかったのは：（1行で言い直す）
今の実装との差分を説明してから修正案を提示してください。まだ直さないでください。
```

**A-7 壊れたとき（戻す→原因→限定修正）**
```text
この修正で（画面）が動かなくなりました。まず修正前の状態に戻してください。
戻したことを確認したら、壊れた原因を説明した上で、影響範囲を（範囲）に
限定した修正案を出し直してください。
```

**A-8 エラー画面**
```text
この操作でエラーが出ました。画面の表示：（そのまま貼る）
直す前に、原因を1文で説明してください。
```

**A-9 2回失敗したら分岐**
```text
この修正は2回失敗しています。アプローチを変えましょう。今のやり方の何が
難しいのかを説明し、別の実現方法を2案、利点欠点つきで提示してください。私が選びます。
```

**A-10 迷子になったら棚卸し**
```text
一旦止めてください。ここまでの変更内容を、画面・データ・その他に分けて
箇条書きで報告し、残作業も一覧にしてください。
```

**A-11 提案の翻訳を求める**
```text
その提案のメリットとデメリット、やらなかった場合に何が起きるかを、
専門用語を使わずに説明してください。私の業務でいうと何に相当しますか。
```

## 場面4：構造変更・データ移行（第3章・第4章・第15章）

**A-12 データ構造の作り替え**
```text
使ってみて、データ構造が実態と合わないことが分かりました。
現状：（例：商談1階層）。実際：（例：顧客›案件›商談の3階層。関係を数行で）
この構造に作り替えてください。条件：
- 既存の入力済みデータは（引き継ぎ方針）で引き継ぐ（消さない）
- 画面上の用語は（自社の言葉）に統一
- 変更前に、影響するテーブルと画面の一覧を先に見せてください
```
→ 構造の間違いはデータが少ない今が一番安く直せる。

**A-13 移行前の書式ゆれ分析**
```text
添付CSV（過去の管理表）を移行する前に、データの健全性を分析してください。
- 日付列の書式は何種類混在しているか（例つきで列挙）
- 空欄・重複・表記ゆれ（同一顧客の別名等）の件数
- 移行時に情報が失われる列はないか
分析結果と「移行ルール案」を先に提示。取込の実装はその後。
取込は何度でも全置換でやり直せる方式にしてください。
```
→ 移行のエラーは実データの「ゆらぎ」から出る。先に棚卸しさせる。

**A-14 実データ規模テスト**
```text
本格運用前の負荷確認をします。（リード1万件・顧客500・案件1,000）規模の
現実的なダミーデータ投入スクリプトを作り、投入してください。その後、全画面で
- 表示が欠落する画面（件数上限・取りこぼし）
- 表示に3秒以上かかる画面
を一覧で報告。ダミーは検証後に一括削除できるようにしておくこと。
```
→ silent切り捨て（第3章の実話）は、量を流さないと見つからない。

## 場面5：進め方の道具（第4章・第8章）

**A-15 現状仕様書を書かせる**
```text
このシステムの現状仕様書を docs/CURRENT_SPEC.md として書いてください。
画面一覧（各1行）／データ構造／外部連携一覧（接続先・用途・認証情報の種類）／
既知の制限。事実だけを書き、実装されていないものは書かないでください。
```

**A-16 作業指示書（WO）の型**
```text
以下の作業指示書に従って実装してください。指示書にない変更はしないでください。
## WO-XX:（件名）
- 目的：（1行）
- 変更範囲：（触ってよい場所）
- やってはいけないこと：（禁止事項）
- 完了条件：（測定可能に）
```

**A-17 ガードレールの導入宣言（毎回の冒頭）**
```text
作業の前に docs/GUARDRAILS.md を読み、全項目に従ってください。
今回の作業でガードレールと衝突しうる箇所があれば実装前に指摘してください。
衝突した場合はガードレールが優先です。
```

## 場面6：外部連携（第14章）

**A-18 接続計画から始める**
```text
（接続先）と連携する機能を作ります。まず接続計画を提示してください：
何と何がつながり、データはどちらに流れ、必要な認証情報は何か、
（接続先）側で私がやる設定は何か（画面つき手順書で）。実装はその後です。
```

**A-19 受け口APIの安全条件つき発注（HPフォーム等）**
```text
（外部システム）からデータを受け取る受け口(API)を作ってください。条件：
- 秘密トークンつきURLとし、トークン不一致は拒否（未設定なら全拒否）
- 受け取ったデータには（流入経路・受信日時）を自動付与
- 重複（同一メール等）は新規作成せず既存に追記
- 先方の担当者に渡す接続仕様書を1枚で出力してください
```

## 場面7：監査・安全（第5章・第7章・第8章・第9章）

**A-20 AI攻撃者レビュー（作った会話とは別の会話で）**
```text
あなたはセキュリティ監査人です。このリポジトリを悪意ある利用者の視点で
監査してください。特に：
- 一覧画面では制限されているのに、検索・集計・API経由なら見えるデータはないか
- 未ログインで実行できる機能はないか
- 秘密キー未設定のとき開いたままになる入り口はないか（fail-open）
- 利用者の入力がそのまま検索条件やリンク先に使われる箇所はないか
所見は「重大度／場所／悪用シナリオ／修正案」の表で。HIGHは私が別ロールで
実測検証できる手順も添えてください。
```

**A-21 性能の先回り監査**
```text
データが今の10倍になった想定で、時間切れや表示欠落が起きる処理を洗い出して
ください。権限チェックが行ごとに繰り返される箇所、一覧が全件取得してから
絞り込む箇所を優先。「現状→安全性を変えずに速くする書き方」を対で提示。
```

**A-22 秘密情報の総点検**
```text
リポジトリ全体から秘密情報の直書きを探してください。APIキー・パスワード・
接続文字列・トークン・それらしい長いランダム文字列。文書とコメントも対象。
見つけたら、場所一覧と環境変数への移し替え手順、再発行（無効化）が必要な
ものの一覧を提示してください。
```

**A-23 本番化ゲートの総仕上げ**
```text
社員展開前の最終確認。以下を実行し結果を表で：
1.未ログインでアクセスできるURL全列挙（0のはず） 2.ロール別の可視範囲一覧
（私の実測用の検証手順つき） 3.秘密情報スキャン（0のはず）
4.DBセキュリティ警告（エラー0のはず） 5.バックアップ設定と復元手順書
想定と違う結果は修正案とセットで報告してください。
```

## 場面8：運用（第9章・第16章）

**A-24 社員向け1枚マニュアル**
```text
社員向けの利用開始マニュアルを1ページで。読者はITに詳しくない営業メンバー。
内容は3つだけ：ログイン方法（初回パスワード変更含む）／最初の1週間でやること
（自分の案件登録・商談後の記録）／困ったときの連絡先。
専門用語なし。画面名は実際のメニュー表記と一致させること。
```

**A-25 週次の変更告知**
```text
今週の変更を社内チャット向けに3行で。変更一覧：（コミットメッセージを貼る）
営業メンバー向けの言葉で、技術用語なし。要望者の名前を入れられるものは
「◯◯さんの要望対応」と入れる。
```
