## 執筆スタイルガイド（全章共通）

### 声（ボイス）の使い分け
- **実録パート**：橋本の一人称（「私は」）。日時・コミット・数字を必ず添えて
  ライブ感を出す。感情や迷いも書く（きれいにしすぎない）
- **標準パート**：二人称（「あなたは」）または中立の解説調。
  実録から抽出した「あるべき手順・仕様・基準」を、読者が実行できる形で書く
- 各章は必ず「実録 → そこから導く標準 → 読者がやること」の順で流す

### 1次情報のルール
- 日時・行数・件数はすべてリポジトリから実測したものだけを書く（推測の数字は書かない）
- コミットハッシュ・設計書ファイル名を脚注的に添え、突合可能な状態を保つ
- 橋本本人にしか分からない記憶（そのとき何を考えたか・何時に起きていたか等）は
  `【橋本追記】` プレースホルダで示し、本人の言葉で埋めてもらう。代筆で創作しない

### 禁止事項
- 「OS」「〜を実現」「〜を可視化」等の機械的な言い回しを地の文で多用しない
  （引用する場合＝コミットメッセージや設計書の原文はそのまま。原文は証拠なので改変しない）
- 「誰でも」「簡単に」「絶対」を使わない
- リスクの記述は必ず対策とセットで書く

### 章の型（テンプレート）
1. 冒頭：この章を読み終えるとできること（1〜3行）
2. 実録（1次情報）
3. 標準（エビデンスに基づく仕様・手順・基準）
4. 読者の実践ステップ（完了条件つき）
5. 章末付録：この章のプロンプト実例 / チェックリスト
6. `【橋本追記】` 一覧（本人が埋める箇所のまとめ）

### 書き手（橋本）のプロフィール事実（本人談・2026-07-31確認）

- 小規模企業の経営者。平日日中は新規商談・研修講師・開発マネジメント・採用面談、
  夜は会食で、平日にまとまった時間はほぼ取れない
- 土日は平日にたまった提案資料・オペレーション改善・マーケティング検討で消える
- その状況を大幅に改善する手段としてCRM/SFA自作を思い立ち、
  **週末にまとまった時間を取って開発を開始**（コミット履歴の週末集中と整合）
- **20代のときは自身も開発者**。ただし**20年以上コードを触っていない**
- 開始にあたり、**普段自社の開発メンバーが使っている手順を下敷きに実施**
  （PR運用・マイグレーション・レビュー等の规律の出所）

> 執筆ルール：書き手を「プログラミング未経験」「非エンジニア」と書かない。
> 正確には「20年以上コードを書いていない経営者」「現代の開発スタックは未知」。
> 開発チームの手順という下地があったことも隠さず、
> 「その下地を持たない読者のために下地ごと教材化した」と位置づける。
