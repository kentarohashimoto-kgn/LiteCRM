# 第9章 本番化ゲート：社員に使わせる前の最終チェック

> この章を読み終えると：「自分だけで使う」から「社員に使わせる」へ進んでよいかを
> 判定する関門（ゲート）を、項目ごとに実行できます。あわせて
> 「ここから先は専門家を入れる」の線引き基準を持てます。

---

## 9-1. なぜ関門が必要か ― 立場が変わる瞬間

自分1人で使っている間、事故の被害者はあなただけです。
社員がログインした瞬間、あなたは**他人のデータと時間を預かる側**になります。
顧客情報が入った瞬間、預かる相手は社外にまで広がります。

この立場の変化は、機能の完成度とは無関係にやってきます。だから
「だいたい動くから社員に配ろう」ではなく、**関門を全項目通過したら配る**、
という手順にします。私のプロジェクトでは、初日にRLSと検証をやり（第2章）、
それでも6週目の監査で4件出ました（第5章）。関門は1回で完璧を保証する
ものではなく、**「少なくともこれを確認せずに配ることはない」という下限**です。

## 9-2. ゲート本体 ― 7区画・全項目

各項目は「確認方法」まで書いています。**すべて実測**です（頭の中の確認は
確認に数えません）。付録Cに印刷用の一覧を収録しています。

### 区画1：認証

- [ ] 未ログインで業務画面のURLを直接開くと、ログイン画面に飛ばされる
  （ブラウザのシークレットモードで全主要URLを実測）
- [ ] パスワードの最低強度が設定されている。初期パスワードは初回変更を案内
- [ ] ログインの機械攻撃対策（CAPTCHA等）がある。
  ※うちは運用3週目に追加しました（7/15）。社員展開前に入れておくのが正解です

### 区画2：権限

- [ ] ロールごとに「見えてよい範囲」の設計表がある（第1章で書いたもの）
- [ ] 実装がデータベース側の制御（RLS）である（画面の出し分けだけではない）
- [ ] **別ロールのアカウントで実測**し、設計表と一致した（件数を数えて記録）
- [ ] 脇道の点検：検索・集計・CSV出力・通知メールの本文からの漏れを確認した
  （第7章の脇道プロンプトを実行）

### 区画3：データ保全

- [ ] バックアップが自動で取られている（サービスの設定画面で確認）
- [ ] **復元の練習を1回やった**（この項目だけは絶対に飛ばさないでください。
  「取れているはず」と「戻せた」の間の距離は、事故の日に思い知ります）
- [ ] 削除は原則ゴミ箱方式（即時物理削除にしない）
- [ ] 自動処理・削除処理の入り口は、合言葉未設定なら全員拒否（fail-closed）

### 区画4：秘密情報

- [ ] コード・文書内に秘密情報が0件（第8章の総点検プロンプトを実行済み）
- [ ] 環境変数の一覧表がある（何のキーが・どこで・何に使われているか）
- [ ] 過去に直書きしたキーは再発行済み（記録に残った値は「漏れた」とみなす）

### 区画5：監視と記録

- [ ] エラーが起きたら気づける仕組みがある（エラー監視ツール。うちはSentryを使用。
  無料枠で十分始められます）
- [ ] 操作の監査ログがある（誰がいつ何をしたか。事故対応の初動が変わります）
- [ ] 機械監査（アドバイザリ）がエラー0の状態である

### 区画6：運用準備

- [ ] 社員向けの1枚マニュアルがある（AIに書かせる。ログイン方法・
  最初にやること・困ったときの連絡先だけでよい）
- [ ] メンバーの発行・停止の手順を、管理者であるあなたが実演できる
- [ ] 「困ったとき」の一次対応を決めた（誰に言う・どこに書く）
- [ ] 変更の告知方法を決めた（うちは週次で「今週の変更」を流しています）

### 区画7：個人情報・法令

- [ ] 保存する個人情報の一覧を書き出した（氏名・連絡先・名刺・録音…）
- [ ] 自社のプライバシーポリシーと矛盾しないか確認した
- [ ] 商談録音のように**相手方が関わるデータ**は、取得の同意・社内の
  取り扱いルールを決めた
- [ ] 退職者アカウントの停止手順がある

## 9-3. 線引き ― ここから先は専門家と一緒に

この教材は「社内の業務システムを、リスクを理解した経営者が自作する」範囲に
責任を持ちます。次のどれかに当てはまるなら、**自作をやめるのではなく、
専門家（セキュリティ診断・開発者・弁護士）を併用してください**。

| 信号 | 状況 | 推奨 |
|---|---|---|
| 🔴 | 決済・送金をシステム内で処理する | 決済は決済代行サービスに委ね、自作側で扱わない |
| 🔴 | 医療・与信など法令上の機微情報を扱う | 専門家の設計レビューなしで進めない |
| 🔴 | 不特定多数の外部ユーザーに公開する | 公開前に第三者のセキュリティ診断 |
| 🟡 | 社外パートナーがログインする | 本教材の範囲内（うちも該当）。ただし権限実測を最重要視 |
| 🟡 | 全社の基幹業務が完全依存し始めた | 年1回の外部監査を予算化する |
| 🟢 | 社内数十名までの業務利用 | 本教材の範囲 |

自分の位置を正直に判定してください。うちは🟡2つの位置にいます。
だから監査を自前で回し（第5章）、いずれ外部診断を入れる前提で
予算を見ています。「全部自分でやる」が目的ではありません。
**「どこまで自分でやれるかを、自分で判断できる」が目的です。**

## 9-4. 展開の初週 ― 配った後の7日間が定着を決める

関門を通過したら配ります。うちの実際の初週運用から。

1. **最初は2〜3人**（全社一斉にしない）。協力的な人から
2. **初日はデータ入力会**を30分。自分の案件を各自3件入れてもらう
   （空のシステムは誰も開きません。自分のデータが入って初めて「自分のツール」になる）
3. **毎日ひとこと感想を回収**（チャットでよい）。要望はためて週末に実装
4. **週次会議をシステムの画面でやる**（第3章の型移植が生きる瞬間です。
   会議で使うツールは、会議のために入力されるようになります）
5. **1週間後に全社展開**。その時点で「先行組の要望を◯件直した」と言えるのが理想。
   直る速さこそ、自作システムが市販SaaSに勝てる最大の体験です

## 9-5. 読者の実践ステップ

| # | やること | 完了条件 |
|---|---|---|
| 1 | ゲート7区画を上から実行 | 全項目にチェックと実測記録がある |
| 2 | 線引き表で自己判定 | 🔴があれば専門家の当てを付けた |
| 3 | 先行2〜3人に展開 | 初日のデータ入力会を実施した |
| 4 | 初週の要望を回収・反映 | 「直した」と言える変更が3件以上 |
| 5 | 全社展開 | 週次会議がシステムの画面で回った |

## 章末付録①：この章のプロンプト実例

**（1）ゲート実行の総仕上げ**

```text
社員に展開する前の最終確認をします。以下を実行し、結果を表で報告してください。
1. 未ログインでアクセスできるURLの全列挙（0件のはず）
2. ロール別に見えるデータ範囲の一覧（私が別アカウントで実測検証します。
   検証手順つきで）
3. コード内の秘密情報スキャン（0件のはず）
4. データベースのセキュリティ警告（エラー0のはず）
5. バックアップの設定状態と、復元手順書
1つでも想定と違う結果があれば、修正案とセットで報告してください。
```

**（2）社員向け1枚マニュアルを書かせる**

```text
社員向けの利用開始マニュアルを1ページで書いてください。読者はITに詳しくない
営業メンバーです。含めるのは3つだけ：
- ログイン方法（URL・初回パスワード変更）
- 最初の1週間でやること（自分の案件を登録する・商談後に活動を記録する）
- 困ったときの連絡先
専門用語を使わず、画面名は実際のメニュー表記と一致させてください。
```
