# マインドマップ機能 設計書（管理者専用） 2026-07

対象: 代表(owner) / 管理者(admin) のみ。営業・BO・人事ロールには一切見えない（DBレベルで遮断）。

## 1. 目的（橋本の使い方）

### ユースケース① 週次の段取り可視化（自動生成 → 手で整形）

Googleカレンダー・CRM/SFA（売上ヨミ・今月/来月のクロージング予定）・週次報告を
横断して取り込み、**1日単位の予定をマインドマップで可視化**する。
前後関係・準備作業の漏れを機械的に検出し、「事前にやるべきこと」を枝として自動で吐き出す。

自動生成したあとは **自由に追加・削除・変更・移動できる**（自動生成は初期値、以後は手編集が正）。

### ユースケース② 研修・セミナー資料の構成検討 / プレゼン実施

構成をマインドマップで考え、そのまま **プレゼンモード**（枝を1画面ずつ辿る）で発表する。
テンプレート（研修・セミナー骨子）と、AIで枝を広げる機能を用意する。

## 3. データモデル（migration `0167_mindmaps.sql`）

```
mindmaps ── mindmap_nodes（自己参照ツリー）
         └─ mindmap_links（枝をまたぐ関連線）
```

### mindmaps
| 列 | 型 | 説明 |
|---|---|---|
| kind | text | `weekly_plan` / `seminar` / `freeform` |
| source | text | `auto`（自動生成） / `manual` |
| period_start | date | 週次のとき対象週（月曜） |
| layout | text | `right`（右方向） / `both`（左右振り分け） |
| owner_user_id | uuid | 作成者（＝橋本） |

### mindmap_nodes
`parent_id` は自己参照（`on delete cascade` かつ **deferrable initially deferred**）。
スナップショット保存で親子をまとめて upsert するため遅延制約が必須。

主な列: `title` / `note` / `sort_order` / `collapsed` / `color` / `marker` / `status` /
`due_date` / `ref_type` / `ref_id` / `ref_url` / `meta(jsonb)`。

`ref_type` は `opportunity` / `account` / `task` / `meeting` / `calendar` / `none`。
自動生成ノードは元レコードを指すので、マップから CRM 詳細に1クリックで飛べる。

### RLS（2026-07-25 改訂：本人限定）
`admin_tenant_ids()`（role in owner/admin）で「管理者だけの機能」であることを担保したうえで、
さらに **`owner_user_id = auth.uid()` で作成者本人だけ**に限定する（`0169`）。
ノード・関連線は `my_mindmap_ids()`（SECURITY DEFINER。mindmaps側のRLSと相互再帰しない）で縛る。

当初は owner/admin なら誰でも全マップを閲覧できる設計だったが、Googleカレンダー連携により
**個人の予定（採用面談・通院・ジム等）がマップに入る**ようになったため、管理者6名に
見える状態は不適切と判断して変更した。**アプリ側の判定が漏れてもDBが拒否する**（多層防御）。

## 4. 自動生成（週次プラン）

### 入力
1. **Googleカレンダー** — 2経路を順に試す。未接続でも CRM だけで生成できる（警告表示）。
   - **① OAuth**（`user_mail_accounts.auth_method='google_oauth'` + `calendar.readonly`）。
     Google Cloud Console の同意画面にスコープ追加が必要。
   - **② iCal非公開URL**（`user_calendar_feeds`）。**Console作業が不要**で、
     「設定 → Googleカレンダー連携」にURLを貼るだけ。URLは実質の認証情報なので
     AES-256-GCM で暗号化保存し、RLS は `user_id = auth.uid()` で本人限定。
     取得先は `calendar.google.com` に限定（ユーザー入力URLによるSSRF防止）。
     繰り返し予定は自前のICSパーサで展開する（`lib/ics.ts`。実カレンダーは50件中18件が繰り返し）。
2. **CRM/SFA** — 対象週のアポ・商談（`meetings` / `opportunities.appointment_at`）、
   今月・来月クロージング予定（`expected_close_date` × `yomi` × 金額 × 確度）、期日タスク。
3. **週次報告** — `weekly_rep_reports.next_week_plan` / `month_ahead_plan`。

### 出力ツリー
```
7/27週の予定
├ 事前準備（今週の仕込み）      ← 検出した漏れ・段取りが集まる枝
├ 7/27(月) … 8/2(日)            ← 1日1枝。下は4分類（下記）
│   ├ 商談 3件                   ← CRMの商談/アポ、CRM顧客に紐づいたカレンダー予定
│   ├ タスク 5件
│   ├ カレンダー 12件            ← 研修・展示会・社内定例など、商談以外の業務予定
│   └ その他 4件（既定で折り畳み）← 移動・休憩・ジムなど段取り上のノイズ
├ 今月クロージング（7月）        ← 金額降順。確度・期日・次アクション付き
├ 来月クロージング（8月）
└ 週次報告メモ                   ← 来週の予定・1ヶ月先の行動予定
```

日付の下を4分類にするのは、実カレンダーでは1日20件超になり、フラットに並べると
週の全体像が読めなくなるため（`classifyEvent`）。分類は CRM紐づき > タイトルのパターン の順で決める。
アポ登録時に自動生成される「予定と同じ内容のタスク」は `dedupeTasksAgainstEvents` で落とす
（「09:30 A社 初回商談(アポ)」と「タスク: 初回商談(アポ) 09:30」の二重表示を防ぐ）。

### CRM ⇔ カレンダーの突合（`mergeCrmAndCalendar`）
同じ商談がCRMとカレンダーで別タイトルで二重に出る（実例: CRM「14:00 ブリックイン福井株式会社
初回商談(アポ)」／カレンダー「14:00 ㈱カトルセ橋本｜予約スケジュール (斉藤純)」）。
① 案件ID、② 同じ日で開始時刻が30分以内、の順に突き合わせて1件に統合する。
統合後は `inCrm` / `inCalendar` が立つので、**片方にしかない予定**を検出できる。

| 状態 | 意味 | 出力 |
|---|---|---|
| CRM＋カレンダー | 正常 | 注記に出どころを表示 |
| CRMのみ | カレンダーに時間を押さえ忘れ | 「カレンダーに未登録の商談 N件」⚑ |
| カレンダーのみ（商談分類） | CRMへの登録漏れ | 「CRMに未登録の商談 N件」 |

カレンダーのみの予定を全部挙げると研修・展示会・社内定例まで並んでノイズになるため、
`classifyEvent` が `meeting` と判定したものだけを挙げる。
カレンダー未連携時は突合の警告を出さない（全件が「未登録」に見えてしまうため）。

### 「事前にやるべきこと」の検出ルール（決定的・AI不要）
| 検出 | 出力 | マーカー |
|---|---|---|
| 今月クロージング予定なのに今週の接点が0件 | 「今週接点なし → 日程打診」 | alert |
| クロージング予定で次アクション未設定 | 「次アクション未設定」 | alert |
| 予定が時間帯で重複 | 「予定重複 → 調整」 | alert |
| 同一顧客の予定が週内に2件以上 | 「◯◯の宿題を△△までに提出」 | flag |
| 期日超過タスク | 「(遅延) タイトル」 | p1 |
| ヨミ・ステージ別の定型準備 | 初回=事前調査/ヒアリング項目、提案=提案書・見積・稟議ルート、クロージング=契約書・決裁者同席 | p2 |

ルールベースなので **APIキー無し・カレンダー未接続でも必ず動く**。
`ANTHROPIC_API_KEY` があり「AIで補強」を選んだ場合のみ、Claude が案件個別の準備項目を追記する。

## 6. 実装方針（描画・編集）

- 追加ライブラリなし。**HTMLノード（絶対配置）＋SVGエッジ**を transform でパン/ズーム。
- レイアウトは純関数 `layoutMindmap()`（`src/lib/mindmap.ts`）。
  子の高さを積み上げ、親を子群の中心に置く古典的 tidy tree。ノード幅は
  全角=1.0 / 半角=0.55 の簡易文字幅計算で見積もり、220px で折り返す。
  `both` レイアウトでは第1階層を左右に振り分けて鏡像配置する。
- 保存は**スナップショット方式**（全ノードを送って差分適用）。個人利用・数百ノード規模なので
  操作ログ方式より単純で壊れにくい。サーバー側で親参照・循環・件数上限(2,000)を検証する。

## 6.1 大きなマップへの対処（2026-07-25 障害対応）

初回リリース時、週次マップが **416ノード・縦約20,000px** になり、拡大やスクロールで
ブラウザのタブが落ちた。原因は2つで、対策も2層に分けている。

### 原因① 生成側 — 無制限に1件1ノードで展開していた
実データは今週の商談9件に対し、**月末締切のタスク122件・期日超過168件**。
これを全部ノードにしたため、`7/31(金)` の枝だけで108ノードになった。

対策: 枝ごとの表示上限（`LIMITS`）と「他N件」への集約、`COLLAPSE_OVER`(8)を超える枝の
既定折り畳み（`autoCollapse`）、および子1つだけのノード（次アクション・日程打診）を
注記へ畳む。結果: **416 → 149ノード / 初期表示40ノード・縦1,616px**。

### 原因② 描画側 — 全ノードをDOMに置いていた
- ホイール1回ごとに全ノードを再レンダリング（ホイールは秒間100回近く発火）
- 縦20,000pxの要素に `transform: scale` が掛かり、ラスタライズ用メモリがGB級に膨張

対策:
- **可視範囲カリング**（`visibleBox` / `nodeInBox` / `edgeInBox`）。画面内＋余白のノードと
  エッジだけ描く。500ノードでも実描画は50未満。編集中・選択中のノードは
  画面外でもDOMに残す（フォーカスと操作対象を失わないため）。
- SVGをマップ全体サイズではなく**可視範囲ぶんの大きさ**にする。
- パン/ズームの state 更新を **requestAnimationFrame で1フレーム1回に間引く**。
- プレゼンモードは折り畳みを無視して全展開するため、同じカリングを適用（余白は
  寄り/引きのアニメーション途中で枝が消えないよう広めに取る）。

生成側だけ直しても、手で育てたマップで同じ事故が起きるため、描画側の対策が本質。
