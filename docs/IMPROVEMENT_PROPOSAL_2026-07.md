# CATORCE Sales OS — 改善提案書（使い勝手・レスポンス・Notion代替性）

> 対象課題（依頼要旨）: 「機能は増えたが使い勝手が向上していない／レスポンスが悪い／まだNotion運用を置き換えるほどの利便性がない」。
> 現状の棚卸しは `docs/CURRENT_SPEC_2026-07.md`。本書はその上での**改善方針と実行計画**。
> 作成日: 2026-07-04 / 対象ブランチ: `claude/keen-mayer-yJCVC`

---

## 0. 結論（先に方針）

3つの症状は、それぞれ別の根本原因を持つ。**「機能を減らす」のではなく「動線を絞り・取得を軽くし・入力をCATORCEに寄せる」**の3本柱で解く。

| 症状 | 根本原因 | 打ち手（見出し） |
|---|---|---|
| 使い勝手が上がらない | 導線が37項目に肥大、類似画面が併存 | **A. IAをコア動線へ再編**（37→約15） |
| レスポンスが悪い | 全業務データを毎回一括取得・force-dynamic多用・メモリ集計 | **B. データ取得の軽量化**（部分取得・キャッシュ・RPC化） |
| Notionを置き換えられない | 入力源がNotion/スプレッド、CATORCEはCSV全置換の閲覧ビュー | **C. 案件をCATORCEで“編集できる”に**（インライン編集・ボード） |

優先順位は **B（体感）→ A（迷わない）→ C（乗り換え）**。Bは即効性が高く、AとCの土台にもなる。

## A. 情報設計（IA）の再編 — 「37項目 → コア動線」

### 課題
- 分析13・exec9で重複（展示会3・セミナー2+取込・ROI4・予測2）。日常業務と週次レビューが混在。

### 提案
1. **トップレベルを5→役割ベースの少数に集約**。例:
   - **今日やること**（ダッシュボード / タスク / 週次レビュー）
   - **案件**（一覧＝ボード/表切替 / 売上予測 / 目標）
   - **顧客**（顧客 / 担当者 / リード / Sランク / 深耕）
   - **分析**（1つの「分析ハブ」に集約。下記2）
   - **経営レビュー**（exec配下は1グループに折りたたみ、レビュー時のみ展開）
2. **「分析ハブ」画面を新設**し、13画面をカード/タブで束ねる:
   - 施策ROI（roi + matrix + channels + product-roi + revenue を**タブ**に統合）
   - 展示会（exhibitions + exhibition-roi + exhibition-select を**タブ**に統合）
   - セミナー（seminars + seminar-followup を統合、取込は画面内アクションへ）
   - トレンド / 営業マン別 / 商品別
   → サイドバーは「分析」1項目、画面内で切替。**導線13→1**。
3. **取込系（CSV）はメニューから外し、各対象画面の「取込」ボタン/モーダルへ**（商談取込・リード取込・セミナー取込・原価取込）。導線から4項目削減。
4. **予測の一本化**: `/forecast` に来期(pipeline)をタブ統合。
5. パンくず + 画面内タブで階層を表現し、サイドバーは**約15項目**に。

### 効果
- 迷いの削減、学習コスト減、モバイル/小画面での操作性向上（既存の最小化機能と併用）。

## B. レスポンス改善 — 「全部取得」をやめる

### 課題（コード根拠）
- `getWorkspace()`（16ページ）が案件+商談+請求+活動+履歴+セミナー等を**毎回一括JSON**で取得（約2MB規模）。
- `force-dynamic` 20ページで毎遷移サーバー再取得。
- 6画面がメモリ集計。

### 提案（効果/コスト順）
1. **【即効】ページ単位の部分取得に置換**
   - 各ページが実際に使うテーブルだけを取る細粒度データ関数へ移行（例: ダッシュボードは `getWorkspaceLite` で十分 → さらに集計はRPCへ）。
   - `getWorkspace` 依存16ページを棚卸しし、詳細が不要な画面は Lite / 専用フェッチャに落とす。
2. **【即効】一覧のサーバーサイド・ページング＋絞り込み**
   - 案件・リード・活動は全件ロードをやめ、`range()` + 条件で必要分のみ。件数は増える前提で設計。
3. **【中】メモリ集計6画面をRPC化**（既存パターン: SECURITY DEFINER + 明示テナント + materialized CTE）。
   - trends / channels / sales-reps / products / seminars / revenue。
4. **【中】キャッシュ戦略の見直し**
   - マスタ系（accounts/products/lead_sources/campaigns/users）は変更頻度が低い → `unstable_cache`（タグ付き）でリクエスト跨ぎキャッシュし、更新時に `revalidateTag`。
   - `force-dynamic` は本当に必要な画面だけに限定。
5. **【継続】インデックス点検**: 集計・絞り込みの結合キー（tenant_id, account_id, expected_revenue_month, source_detail, marketing_channel_id 等）にインデックスが効いているか `explain` で確認。
6. **計測の常設**: 主要ページの TTFB / RPC 実行時間をログ化し、リグレッションを検知。

### 目標（目安）
- 主要ページ初期表示のサーバー処理を現状比で体感的に半減。案件/リード一覧は件数非依存の応答に。

## C. Notion代替性 — 「見るだけ」から「使う」へ

### 課題
- 入力源が Notion（商談ヨミ表）+ スプレッドシート。CATORCEはCSV全置換の閲覧・分析ビュー。日常編集がCATORCEで完結しない。

### 提案（段階導入）
1. **案件のインライン編集**（最優先）
   - 一覧/詳細で ヨミ・確度・見込月・見込額・次回アクション・担当 を**その場で編集→即保存**（既存 `updateOpportunityAction` を活用、楽観的更新）。
   - これにより「Notionで更新→CSV→全置換」を廃し、CATORCEを一次入力に。
2. **ヨミ表ボード（カンバン）ビュー**
   - Notionのボード運用に相当。列＝ヨミ(0受注〜9調整中)、カード=案件。ドラッグでヨミ変更→保存。表/ボード/カレンダー切替。
3. **保存ビュー & クイックフィルタ**
   - 担当・ヨミ・流入元・期間・金額で絞り込み、名前を付けて保存（Notionのビュー相当）。
4. **移行戦略の確定（要意思決定 → 第4章）**
   - (a) CATORCEを商談の一次システムにし、Notionは段階廃止 / (b) 当面は定期CSV取込を維持しつつ「差分マージ取込」に改善（全置換をやめ、外部キーで突合更新）。
5. **議事録/事前情報の一次化**
   - `meetings` の事前情報+議事録をCATORCE上で編集可能に（現状は取込時のみ生成）。

### 効果
- 二重管理の解消、最新化ラグの解消、Notion脱却の現実的な道筋。

## D. 実行ロードマップ（案）

| フェーズ | 内容 | 主な成果物 | 目安 |
|---|---|---|---|
| **P0 計測** | 主要ページの実行時間ログ、getWorkspace依存の棚卸し | 計測ダッシュボード/棚卸し表 | 小 |
| **P1 体感改善(B)** | 部分取得への置換、一覧ページング、キャッシュ見直し | 高速化された主要ページ | 中 |
| **P2 動線再編(A)** | 分析ハブ統合、取込のボタン化、サイドバー約15項目化 | 新IA・分析ハブ画面 | 中 |
| **P3 一次入力(C)** | 案件インライン編集＋ボードビュー＋保存ビュー | Notion代替の案件UX | 中〜大 |
| **P4 移行(C)** | 全置換→差分マージ or Notion段階廃止 | データ運用の一本化 | 大（要判断） |
| **P5 整理** | 未使用画面の廃止、actions.ts分割、RPC集約 | 保守性向上 | 中 |

> AとBは並行可能。まずP0→P1で体感を改善し、成果を見ながらP2/P3へ。

## F. 意思決定が必要な論点（次のステップの前提）

1. **移行方針**: 商談の一次システムをCATORCEに寄せる（Notion段階廃止）か、当面はCSV運用継続（ただし全置換→差分マージ）か。
2. **優先度**: 「まず速く（B）」で合意でよいか。それとも「まずNotion代替（C）」を先行したいか。
3. **exec（経営レビュー）**の利用頻度: 常設メニューに残すか、レビュー時のみのモードにするか。
4. **一覧の主役ビュー**: 案件は「表」中心か「ボード」中心か（デフォルト表示の決定）。
5. **対象データ量の想定**: 今後1年の案件/リード想定件数（ページング設計の前提）。

## 付録: 変更しても壊れない原則（従来方針の踏襲）
- 加算的アプローチ（既存テーブル/RLSを壊さない、列追加 or 付随テーブル）。
- 重い集計は SECURITY DEFINER + 明示テナント + materialized CTE のRPCに寄せる。
- 破壊的操作は `can_edit_role()` ガード、authenticated限定、`search_path`固定。
- ブランチ運用・機微情報の非コミットは現行ルールを継続。
