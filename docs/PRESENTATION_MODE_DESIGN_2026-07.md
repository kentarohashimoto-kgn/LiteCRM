# プレゼンモード（ダミーデータ切替）設計・工数検討 2026-07

## 1. 背景・目的

カトルセCRMを営業提案の「実演デモ」として使いたい。ただし実データを見せると
経営数値・顧客情報の漏洩リスクがあるため、**各営業マンがワンタッチで
「プレゼンモード」に切り替えると、全メニューがそのままリアル感のある
ダミーデータで動作する**状態を実現する。

出口戦略（横展開インストール / ゼロからバイブコーディング）の両方で、
「いつも使っている画面をそのまま見せる」ことが最大の説得材料になるため、
デモ専用の別アプリではなく **本番アプリそのものを安全に見せる** ことがゴール。

## 2. 現行アーキテクチャの要点（調査結果）

設計判断に直結する事実：

| 項目 | 現状 |
|---|---|
| マルチテナント | 全業務テーブル（116テーブル）に `tenant_id`。RLSで `memberships`（user_id→tenant_id, role）経由の完全分離 |
| テナント解決 | `src/lib/session.ts` の `getCtxOrNull()` に**一元化**。activeなmembershipを1件取得して `ctx.tenantId` を決定。83ファイルがここ経由 |
| データ取得 | `src/lib/data/*`・Server Actions は `ctx.tenantId` + RLS でスコープ。テナントを跨ぐ読み書き経路はほぼない |
| 担当者スコープ | `owner_user_id` は実ユーザー（auth.users）を参照。「自分の案件」系画面はこれでフィルタ |
| シード実績 | `supabase/seed.sql` にテナント単位のマスタ投入パターンあり。`0035_purge_tenant_opportunities.sql` にテナント単位パージの前例あり |
| ⚠️ 単一テナント前提 | `api/cron/daily-digest`・`api/lead-intake` などが `from("tenants").select("id").limit(1)`（**順序指定なし**）でテナントを取得。`api/cron/xray-snapshot` は全テナントを走査 |

**結論：マルチテナント基盤が既に完成しているため、「デモ専用テナント」を
1つ作り、プレゼンモード＝アクティブテナントの切替、とするのが圧倒的に安い。**
画面・データ関数・RLSは一切変更不要で、全メニューが自動的にダミーデータで動く。

## 3. 実現方式の比較

### 方式A：デモテナント + アプリ内モード切替（★推奨）

デモテナント（例: slug `demo`）にダミーデータを投入。各営業マンに
デモテナントのmembershipを追加し、トップバーのトグルで
「プレゼンモード」Cookieをセット。`getCtxOrNull()` がCookieを見て
デモテナント側のmembershipを優先するだけで、**全83画面が無改修で切り替わる**。

- 長所: ログインしたまま瞬時に切替（プレゼン中の体験が良い）／実装が薄い（session.ts + トグルUI + バナーのみ）／RLSによる分離が既に効いており、モード中に実データが混ざる経路が構造的にない
- 短所: デモデータの作成・鮮度維持という運用資産が必要（これは全方式共通）／単一テナント前提のcron等の修正が必須（§4.6）

### 方式B：プレゼン専用ID（デモテナント専属ユーザーでログインし直す）

コード変更ゼロ。デモテナントだけに所属する `demo@catorce.jp` 的な
ユーザーを作り、営業マンは別ブラウザプロファイル/シークレットウィンドウで
ログインして見せる。

- 長所: 即日運用可能（データ投入のみ）。方式Aの土台（デモテナント）と完全に共存する
- 短所: プレゼン中のログアウト/ログイン切替が不格好／パスワード共有の運用課題／「自分のアカウントで使っている感」が薄れる

→ **方式Aの先行リリース（Phase 0）として採用価値あり。捨てコストゼロ。**

### 方式C：アプリ内データモック層 / テストメニューとデータ毎の切替

データ取得層でモード判定してフィクスチャを返す、またはメニュー＋データを
セットで複製する方式。

- 短所: `src/lib/data` 40モジュール + Server Actions + RPC 多数への横断改修。以後の全機能追加で二重メンテ。RPCやRLS前提の集計（dashboard_metrics等）はモック困難
- **判定: 却下。** 工数が方式Aの5〜10倍で、本番コードにデモ用分岐が散らばり品質リスクになる

## 4. 推奨方式（A）の詳細設計

### 4.1 デモテナントの作成

- マイグレーション: `tenants` に `is_demo boolean default false` を追加し、
  デモテナント（固定UUID・slug `demo`）を投入
- マスタ（lead_sources / products / campaigns / tenant_settings / sales_targets）は
  `seed.sql` を雛形に架空社名「株式会社〇〇（デモ）」向けへ差し替え
  — READMEにも「他テナント展開時はseedを複製」と書かれている想定通りの使い方

### 4.2 モード切替（コード変更の中心。変更は3ファイル+α）

1. `src/lib/session.ts`: Cookie `presentation_mode=1` があり、かつユーザーが
   デモテナントのmembershipを持つ場合はそちらを `ctx` に採用
2. Server Action `togglePresentationMode()`: Cookieの set/unset。
   初回はデモテナントへのmembership自動付与（本番テナントのactiveメンバーのみ・roleは `sales_manager` 相当で全件閲覧可）
3. トップバー: トグルボタン + **モード中は画面上部に常時バナー**
   （例: 紫帯「🎦 プレゼンモード — 表示中は全てダミーデータ」）。
   誤って実データでプレゼンする事故と、その逆（デモのまま業務する事故）の両方を防ぐ

### 4.3 ダミーデータ設計（工数の最大要素）

- **対象**: 主要画面が「使い込まれて見える」ために必要な20〜30テーブルに絞る
  （accounts / contacts / leads / opportunities / opportunity_products /
  activities / tasks / meetings / stage_histories / forecast_snapshots /
  sales_targets / billing_schedules / touchpoints / seminars / exhibitions 系）。
  116テーブル全部は埋めない。HR・PMO等のBO系はPhase 2
- **リアル感の要件**:
  - 架空だが実在感のある日本企業名・人名・案件名（生成AIで一括生成）
  - 商談はステージ/ヨミ/金額の分布を実運用に近い比率で（受注・失注・停滞・today表示分を含む）
  - **日付は「今日」からの相対値で生成**（リセット時に再計算）。
    プレゼンがいつでも「今週の動き」があるように見える
- **担当者の付替え**: 「自分の案件」系画面のため、リセット実行者
  （＝プレゼンする営業マン）に主要案件の `owner_user_id` を割り当てる。
  残りはデモテナントに追加した架空メンバー（membershipなしのprofile表示は
  要検証、必要なら他の実営業メンバーに分配）

### 4.4 リセット機能

- 設定画面 or トグルメニューに「デモデータを初期化」ボタン
- 実装: RPC `reset_demo_tenant(presenter uuid)` — デモテナントの業務データを
  パージ（`0035` の前例あり）→ テンプレートから相対日付で再投入 → owner付替え
- プレゼン中の編集・作成は自由（むしろ「その場で入力できる」デモになる）。
  終わったらリセットで原状回復

### 4.5 安全ガード

- メール送信（SMTP/Gmail）・IMAP同期・シーケンス実行: `ctx` がデモテナントの
  場合は送信系アクションを無効化（ボタンは見せてよいが実行はブロック）。
  そもそもデモテナントにはメール認証情報を設定しない、の二重防御
- 開封トラッキング等の外部発信も同様にスキップ

### 4.6 単一テナント前提コードの修正（**方式Aの必須前提**）

現状 `limit(1)`（順序なし）でテナントを取るコードは、テナントが2つになると
**どちらを掴むか不定**になる。特に `api/lead-intake` は実リードがデモテナントに
入る事故につながるため、以下を `is_demo = false` フィルタ or slug指定に修正:

- `src/app/api/lead-intake/route.ts:67`
- `src/app/api/cron/daily-digest/route.ts:116,150`
- `src/app/api/cron/xray-snapshot/route.ts:32`（全走査→ `is_demo=false` に）
- その他cron（automation / sequences / pmo-nightly / inbound-sync / recordings）の
  テナント走査有無を実装時に総点検

## 5. 工数見積り

前提: バイブコーディング（Claude Code併用）での実働目安。1日=集中作業1日。

| フェーズ | 内容 | 工数 |
|---|---|---|
| **Phase 0**（任意・即日） | デモテナント+マスタ投入、プレゼン専用ID発行（方式B運用開始） | 0.5〜1日 |
| **Phase 1-1** | マイグレーション（is_demoフラグ、デモテナント）+ 単一テナント前提の修正（§4.6） | 1日 |
| **Phase 1-2** | ダミーデータ生成スクリプト（主要20〜30テーブル、相対日付、分布調整） | 2〜3日 |
| **Phase 1-3** | モード切替（session.ts / トグルAction / バナーUI） | 1日 |
| **Phase 1-4** | リセットRPC + owner付替え + 初期化ボタン | 1日 |
| **Phase 1-5** | 送信系ガード + cron除外の総点検 | 0.5〜1日 |
| **Phase 1-6** | 全主要画面の見栄え確認・データ微調整（プレゼンリハーサル込み） | 1〜2日 |
| **Phase 1 合計** | | **6.5〜9日** |
| **Phase 2**（後日） | BO系（HR/PMO/経理）画面のデモデータ、日付自動ロール（夜間cron）、提案シナリオ用ストーリーデータ（例:「展示会→リード→受注」の一連の流れを仕込む） | 2〜4日 |

最短経路: **Phase 0 だけなら今週中にプレゼン可能**。Phase 1 完了で
「各営業マンが自分のIDのままワンタッチ切替」が実現。

## 6. リスクと対策

| リスク | 対策 |
|---|---|
| 実データ露出（切替忘れ） | 常時バナー + モード中の配色変更。切替はワンタッチなのでプレゼン直前に必ず実施できる |
| 実リード/メールがデモ側に流入 | §4.6 の修正を Phase 1-1 で最優先実施。デモテナントにメール認証情報を置かない |
| スキーマ進化でデモデータが陳腐化 | 生成スクリプトをリポジトリ管理し、新機能追加時のチェックリストに「デモseed更新」を追加 |
| プレゼン中の編集でデータが荒れる | リセットボタンで原状回復（§4.4） |
| デモのまま業務入力してしまう | バナー + Cookie有効期限を短め（例: 12時間）に設定 |

## 7. 微調整で決めたい事項（実装前の確認ポイント）

1. デモテナントのロール: 全営業に `sales_manager`（全件閲覧）でよいか、
   実運用と同じロール分担を再現するか
2. ダミーデータの規模感: 顧客何社・商談何件・期間何ヶ月分に見せたいか
   （目安案: 顧客80社 / 商談150件 / 12ヶ月分の実績）
3. 商材マスタ: カトルセの実商材のまま見せるか、汎用商材に差し替えるか
   （横展開提案なら実商材のままの方が説得力がある、という判断もあり）
4. Phase 0（プレゼン専用ID）を先行させるか、Phase 1 一括か
5. デモ中の編集可否: 自由編集+リセット（推奨）か、閲覧専用か
