## 0. 結論(3行)

1. **土俵が違う**。JUST.DB は「業務システムを自分で作るためのノーコード基盤」、
   カトルセCRMは「営業のやり方まで作り込み済みの営業OS」。
2. JUST.DB を CRM として使う場合、**顧客管理テンプレートを起点に自社で組み立てる**
   ことになる。ヨミ・週次レビュー・売上逆算・営業レントゲンといった
   「営業マネジメントの型」は**自前で設計・構築する対象**になる。
3. 逆に、**全社の非営業業務(生産・在庫・経費・稟議・手書き帳票のデジタル化)まで
   1基盤で覆いたい**なら JUST.DB が強い。カトルセCRMは営業〜デリバリー〜粗利の
   縦串に特化しており、汎用ノーコード基盤ではない。

## 3. 料金・コスト構造

| 項目 | JUST.DB | カトルセCRM |
|---|---|---|
| 課金方式 | **同時ログインライセンス**(アカウント数でなく同時接続数) | 自社利用のため実費(インフラ+開発)。外販形態は未決定 |
| 参考価格 | 1ライセンス **15,000円/月(税別)** 、**最低5ライセンス**〜。ベーシックパッケージは **月額99,000円(税別)〜** | インフラ実費 約¥7,000/月規模(Vercel+Supabase)+開発コスト |
| 初期費用・導入支援 | 別途(要見積) | — |
| AI機能の課金 | 生成AI/AI-OCRは製品標準(詳細条件は要確認) | ユーザー単位の追加課金なし(夜間バッチ運用) |
| 構築工数 | **自社 or パートナーの設計・構築工数が別途発生** | 発生しない(既に構築済み) |
| 標準上限(要確認) | データフロー有効件数 リアルタイム150/スケジュール150、APIコール 5,000回/日・30回/分、ファイルストレージ 100GB | Supabaseプラン依存 |

**課金方式の実務的な意味**:
同時ログイン課金は「全社に配って、使うのは一部」という**閲覧者が多い全社システム向けにコスト効率が良い**。
逆に「営業10人が朝から晩まで常時ログインして使う」用途では**ほぼ人数分のライセンスが必要**になるため、
ユーザー課金との差が消える。営業CRM専用途では価格優位が出にくい点は突ける。

## 5. 権限・セキュリティの思想差(提案で効く論点)

- **JUST.DB**: フォルダー/データテーブル/業務プレート/パネル単位で
  ユーザー・グループのアクセス権を設定する**アプリケーション層の制御**。
  オンプレ選択でネットワーク的な閉域運用が可能。
- **カトルセCRM**: PostgreSQL の **Row Level Security による DB 層の制御**。
  アプリにバグがあっても他テナント・他担当のデータ行そのものが返らない。
  外部営業パートナーとの協業前提で「自分の担当案件しか見えない」を DB で担保。

→ 「外部パートナー・業務委託を営業に混ぜる」体制なら RLS の説明が効く。
→ 「オンプレ必須・閉域必須」の情シス要件なら JUST.DB が勝つ。

## 6. どちらを選ぶべきか(ケース別判定)

| 状況 | 推奨 | 理由 |
|---|---|---|
| 営業のヨミ管理・週次会議・売上予測を今すぐ回したい | **カトルセCRM** | 型が実装済み。JUST.DBだと設計から |
| 営業だけでなく**生産・在庫・経費・稟議まで**1基盤にしたい | **JUST.DB** | 汎用基盤の土俵。カトルセは非対応 |
| **手書き帳票・紙運用**のデジタル化が主要課題 | **JUST.DB** | AI-OCR標準搭載 |
| 稟議・合議・代理承認など**日本型の承認フロー**が業務の中心 | **JUST.DB** | 標準機能。カトルセは固定実装のみ |
| 情シスが**自分で作り変え続けたい** | **JUST.DB** | ノーコード改修の主導権が社内に残る |
| 情シスが薄く、**作る人がいない** | **カトルセCRM** | 構築工数ゼロ。ノーコードは「作る人」が要る |
| **オンプレ・閉域**が要件 | **JUST.DB** | クラウド/オンプレ選択可 |
| 名刺→リード→商談→受注→案件粗利まで**一本で見たい** | **カトルセCRM** | 単一DBで縦串が通っている |
| 議事録AI・メール追客・スコアリングを**追加課金なしで** | **カトルセCRM** | 夜間バッチ運用で従量課金なし |
| 全社数百人に配布、大半は**閲覧のみ** | **JUST.DB** | 同時ログイン課金がコスト効率で有利 |

## 7. 提案時の使い分け(営業トーク骨子)

### カトルセCRM側の勝ち筋
1. **「ノーコードは"作れる"であって"できている"ではない」** — JUST.DBで営業管理を
   作るなら、ヨミの定義・週次会議の設計・予測ロジックを自社で決める必要がある。
   その設計こそが一番難しい。カトルセCRMはそこが答えとして入っている。
2. **「BIでもDBでもなく、処方箋を出す」** — 売上方程式に因数分解して打ち手を出す
   営業レントゲンは、汎用DB基盤の延長線上には出てこない。
3. **「議事録がヨミになる」** — 録音→文字起こし→AI要約→人の確認→商談フィールド更新
   が1本のパイプライン。追加課金なし。
4. **DB層(RLS)の権限分離** — 外部営業・業務委託と協業する体制での説明力。

### JUST.DBが勝つ場面(正直に認めるべき点)
1. **AI-OCR / 手書き帳票のデータ化** — カトルセCRMには入口がない(名刺OCRも未実装)。
2. **稟議・合議・代理承認のワークフロー** — 日本商習慣対応を製品として謳っている。
3. **帳票出力(見積書・請求書のExcel/PDF)** — カトルセは請求書発行が未実装。
4. **カスタム項目・テーブルの自由追加** — カトルセはスキーマ固定。
5. **営業以外の全社業務** — 生産・在庫・勤怠・経費。カトルセは明示的に非対応。
6. **オンプレミス** と **ベンダーとしての継続性**。

### 併用シナリオ(競合ではなく棲み分け)
「基幹・バックオフィスはJUST.DB、営業フロントはカトルセCRM」は成立する構成。
両者を敵対させず、**営業マネジメントの型だけは専用品で持つ**という提案が最も通りやすい。
