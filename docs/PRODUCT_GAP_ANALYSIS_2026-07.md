# CRM/SFA プロダクトギャップ分析・アクションアイテム（2026-07）

> **目的**: カトルセ専用フルカスタムの現CRM/SFAを「パッケージ化して外販できる製品」へ進化させるための、機能・非機能・パッケージ化観点のギャップ分析と優先度付きアクションリスト。
> **評価方法**: 2026-07-05時点のコードベース・本番DBを実査した証跡ベース（推測ではなくgrep/SQL/設定の確認結果）。市販CRM/SFA（Salesforce/HubSpot/Zoho/Mazrica等）の標準機能セットと比較。
> **関連**: `docs/exec-plan/`（実行計画）/ `docs/CURRENT_SPEC_2026-07.md`（as-is仕様）

---

## 0. エグゼクティブサマリー

**現状の強み**: 営業プロセスの型化（ヨミ・分類・承認・トランジション・お土産）は市販CRMより踏み込んでおり、外販時の差別化になる。RLSマルチテナントの土台・重集計のRPC化・楽観ロックなど、スケールの基礎はできている。

**最大のギャップは機能ではなく「製品としての足腰」**:
1. **品質保証ゼロ**（自動テスト0件・監視0・エラーバウンダリ0・監査ログ未記録）→ 外販すると障害対応・説明責任が果たせない
2. **シングルテナント前提の残骸**（新規テナントに画面が立ち上がらない：オンボーディング不在、定数のハードコード、seedの手動性）
3. **性能改善が道半ば**（9ページが2.1MBのworkspace_full、17ページが1.3MBのlite、リード11.6MBテーブルの画面が残る）

**推奨**: 「P0=外販の前提条件（品質・セキュリティ・テナント分離検証）」→「P1=パッケージ化基盤」→「P2=機能ギャップ」の順。機能追加より先に足腰。

## 2. パッケージ化・外販 readiness

| # | 項目 | 現状（証跡） | ギャップ |
|---|---|---|---|
| P1 | **テナントオンボーディング** | 新規tenant作成のフローなし。seedは既存全tenantへのINSERT移行のみ。**今、2社目を作ると空画面＋初期マスタなし** | サインアップ→tenant作成→初期マスタ投入→管理者招待の自動化が必要 |
| P2 | **ブランディング/名称** | `APP_NAME="CATORCE Sales OS"`、`CATORCE_LEAD_SOURCES`等が`constants.ts`にハードコード | テナント設定(tenant_settings jsonb)からの読込に置換 |
| P3 | **業務定義のテナント化** | ヨミ(0-9)・ステージ・案件予測・会計年度(7月開始)・スコア重みがコード定数。カトルセの営業言語が全テナントに強制される | 「ラベル/閾値はテナント設定、変換ロジックはキー固定」の2層化。会計年度開始月のテナント設定化 |
| P4 | **プラン/課金** | なし | 外販形態（SaaS月額 or 導入型）の決定が先。SaaSならStripe+プラン別機能フラグ |
| P5 | **業種特化画面の切出し** | 展示会/セミナー/エンゲージメント等はカトルセのGTM特化 | 「コアCRM」と「マーケ分析パック」をモジュール分割し、テナント毎に有効/無効化（feature flags） |
| P6 | **データ移行キット** | Notion/リードCSV取込は個別実装 | 汎用CSVマッピング取込（対象エンティティ選択式）へ一般化。乗換導入の武器になる |
| P7 | **監査証跡** | `audit_logs`テーブルは存在するが**アプリから一切書込なし** | 全更新系アクションで記録（誰が/いつ/何を/before-after）。B2B外販の必須要件 |
| P8 | **i18n** | 日本語ハードコード | 国内特化なら当面不要（意思決定として明記推奨） |

## 3. 非機能ギャップ

### 3.1 品質保証（最重要・現状ゼロ）
- **自動テスト0件**（package.jsonにテストランナーなし）。ヨミ変換・スコアリング・予測集計・CAS等のビジネスロジックは純関数化されておりテスト容易なのに未着手。リグレッションは目視のみ。
- **CI/CDゲートなし**: buildは手動確認。PR時のtypecheck/test/lintの自動実行なし。
- **RLSテストなし**: テナント分離・ロール別可視性を検証する自動テストがない。**外販で最も事故が許されない箇所**。

### 3.2 可観測性・運用（現状ゼロ）
- エラー監視なし（Sentry等未導入）。本番エラーはユーザー申告でしか気付けない。
- `error.tsx`（エラーバウンダリ）が1つもない。サーバーエラー時はNext.js既定の白画面。
- 構造化ログ・遅延計測なし（`[perf]`ログ構想は未整備）。遅いRPCの継続監視ができない。
- バックアップ/DR方針が文書化されていない（Supabase PITRの有効状態・復旧手順・RTO/RPO未定義）。

### 3.3 性能（改善済みだが残件あり）
- 改善済み: ダッシュボード10KB化・案件/顧客一覧のサーバーページング・詳細ページのスコープ取得。
- **残件**: `getWorkspace()`(2.1MB) 9ページ（activities/contacts/reviews/分析4画面/leads配下2）、`getWorkspaceLite()`(1.3MB) 17ページ。activities一覧は全件ロード。カレンダーは最大5000件を一括取得。`meeting_count`は相関サブクエリ（案件数万件で劣化）。
- リード基盤はテーブル11.6MB・8,271件で今後最も速く成長する領域。person_engagement/touchpointsの再計算(`recompute_engagement`)のスケール特性が未検証。
- 同時利用増への備え: 楽観ロックは案件系のみ。活動/顧客編集・マスタ編集は後勝ち上書き。

### 3.4 セキュリティ
- 良い: RLS全テーブル・SECURITY DEFINER最小権限・service roleのサーバー限定・advisor ERROR=0運用。
- **残**: 漏洩パスワード保護OFF（ダッシュボード設定、以前から未対応）／MFAなし／レート制限なし／セッションポリシー未定義／CSVアップロードのサイズ・型検証が薄い／`external_sales`ロールの可視範囲の仕様書がない。

### 3.5 スケーラビリティ（利用者増の想定）
- Vercel Hobby＋Supabase無料/低層と推定。外販時はPro/Team層＋接続プール（現状はSupabase接続をリクエスト毎生成、PgBouncer前提の確認要）。
- テナント数増でRLS `current_tenant_ids()`のmemberships参照が全クエリに乗る。インデックスは現状十分だが、テナント100超を想定するならRLS性能の負荷試験が必要。

## 5. 推奨ロードマップ

```
フェーズ1（〜1ヶ月）「壊れない製品」        : A-01〜A-08 ＋ C-04（残存性能）
フェーズ2（1〜2ヶ月）「2社目が入る製品」    : B-01〜B-06 ＋ B-07の意思決定
フェーズ3（2〜4ヶ月）「選ばれる製品」        : C-01〜C-03, C-05〜C-08
フェーズ4（判断次第）「伸びる製品」          : C-09/C-10, D群
```

**理由**: 外販の失注理由・解約理由になるのは「機能不足」より「データ消失・障害・他社データ混入」。P0はすべて、起きたら製品が終わるリスクの保険であり、かつ現在のコード品質（純関数化・RPCパターン統一）なら安価に入れられる。P1は「カトルセ専用の前提」を剥がす作業で、後回しにするほど剥がすコストが増える。

## 6. すぐ決めていただきたいこと（経営判断3点）

1. **B-07 外販形態**: SaaS型（自社運用・月額課金）か、導入支援型（顧客毎に環境構築）か。マルチテナント設計の深さ・課金基盤・サポート体制がここで分岐します。
2. **ターゲット業種**: カトルセ同型（AI研修/受託のB2B営業）に絞るか、汎用CRMとして広げるか。絞るなら展示会/セミナー分析・営業プロセスの型がそのまま差別化になり、B-03/B-04の工数を抑えられます。
3. **品質投資の承認**: フェーズ1（テスト・監視・監査・分離検証）は画面が増えない投資ですが、外販の前提条件です。先行実施の承認をお願いします。
