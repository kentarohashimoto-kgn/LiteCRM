> **目的**: 2024年に検討・試行した「顧客ベースメルマガ配信管理（案3）」（Google スプレッドシート＋Apps Script。Drive上に平石版/石本版/識祭リスト版が現存）を、現在のLiteCRMを前提に再検討する。
> **前提資料**: `docs/EMAIL_WORKFLOW_AUTOMATION_SPEC_2026-07.md`（F-101/F-102）/ `docs/LEAD_TO_APPOINTMENT_DESIGN_2026-07.md`（F-201〜F-206。大半実装済み）

> **本書はコード変更を含まない設計・意思決定文書**。合意後にワークオーダーへ分解して実装する。

## 0. 先に結論

1. **新規のメルマガ基盤は作らない**。前回検討（2024年）当時は送信・計測・履歴の全部を自作する必要があったが、その後 **リード一括メール（F-203系）として同等以上の基盤が本番稼働済み**。テンプレ差し込み・本人アカウント送信（SMTP/Gmail OAuth）・開封/クリック計測・配信停止（特電法対応）・予約送信・セグメント履歴・反応分析・日次300通ガードまで揃っている。
2. **やるべきことは「対象をリードから顧客（担当者=contacts）へ広げる」拡張だけ**。送信パイプラインは丸ごと流用できる。`email_messages` / `scheduled_emails` は設計当初から `contact_id` / `account_id` 列を持っており、CRM側への拡張は織り込み済み。
3. スプレッドシート版の目的4点（カテゴリ別配信 / 企業別開封率 / 配信別開封率 / 営業状況の一元管理）は、**差分実装3〜4本（規模: 中）**ですべて充足できる。
4. 実装前に決めたい論点は §5 の6点（対象単位・リードとの重複送信防止・カテゴリの持ち方・送信上限・UIの置き場・運用ルール）。

## 1. 前回検討（スプレッドシート版）の振り返り

**目的（原文より）**
- 企業のニーズにあった情報を届けてWin-Winになる
- 企業を主軸としたメール配信の管理をできるようにする
- 企業をカテゴリ分類して、カテゴリにあったメールを配信できるようにする
- 企業へ配信されたメールの開封率を確認し、ニーズを数値で評価できるようにする
- メール配信ごとに開封率を確認し、企画のニーズを数値で評価できるようにする
- 営業状況を一元管理して営業計画を効率化する

**仕組み**: 企業リスト（会社名・担当者・メール・流入元・役職レベル・カテゴリ分類）＋メールテーマ列に「〇」を付けて対象選定 → Apps Scriptが10秒に1通送信 → MailOpenシートに開封記録。`{{企業名}}` `{{担当者}}` の差し込みに対応。

**限界（再検討の動機）**
- リストが人ごと・用途ごとにスプレッドシートとして複製され（平石版/石本版/識祭リスト版…）、**マスタが分散**。CRM（accounts/contacts）と二重管理。
- **配信停止・バウンスの管理がない**（特電法の表示義務・List-Unsubscribeヘッダ非対応。ドメイン評価リスク）。
- 送信上限・重複送信の制御がなく、送りすぎ・二重送信を人力で防いでいた。
- 開封記録はあるがボット/プロキシ開封の除外がなく精度が低い。営業データ（商談・架電）との突合も手作業。

## 2. その後の状況変化 — 流用できる実装済み資産（実査 2026-08-02）

リード獲得〜アポのために構築した一括メール基盤。**すべて本番稼働中**。

| 資産 | 実体 | 本件での流用 |
|---|---|---|
| 送信コア | `deliverTrackedEmail`（`mail-deliver.ts`）。本人アカウント（SMTP/Gmail OAuth・`user_mail_accounts`）から順次送信 | そのまま流用 |
| テンプレ | `email_templates`（`0143`）。`{contact}` `{company}` `{sender}` `{signature}` 差し込み＋送信直前の直接編集 | そのまま流用（スプレッドシートの`{{企業名}}`等と同等） |
| 開封/クリック計測 | `email_events` / `email_links`（`0144`）＋ボット・プロキシ開封の除外（`0178`/`0179`） | そのまま流用（前回より精度が高い） |
| 配信停止・特電法 | `mail_suppressions`（`0172`）/ 本文フッター＋List-Unsubscribeヘッダ / 広告宣伝判定の注意喚起（`detectAdSignals`・PR #130） | そのまま流用（前回の最大の欠落を解消済み） |
| 予約送信 | `scheduled_emails`＋cron（`0179`）。**`contact_id`/`account_id` 列あり** | そのまま流用 |
| セグメント履歴・反応分析 | `lead_mail_batches`（`0173`）＋ `/app/email/segments`（送信/開封/クリック/返信率） | 汎用化して流用（§4 D3） |
| ガードレール | 1回300件・送信者ごと日次300通・サプレッション突合・同一テンプレ再送防止・アドレス重複除外（`lead-mail.ts`） | そのまま流用 |
| 一括送信UI | `BulkMailPanel`（テンプレ選択→対象内訳プレビュー→直接編集→確認→チャンク送信/予約） | ほぼそのまま流用（対象抽出だけ差し替え） |
| CRM側の受け皿 | `email_messages.contact_id / account_id / opportunity_id`（`0143`当初から） | 送信ログの顧客紐付けに使用（追加マイグレーション不要） |
| 顧客マスタ | `accounts`（業種/規模/ステータス/優先度）・`contacts`（部署/役職/役割/温度感/**interest_topics text[]**/メール） | 配信対象の抽出軸。カテゴリ分類の受け皿候補 |

**ギャップは「対象抽出（contacts×accounts）とそのUI」および「顧客軸の反応集計」のみ。**

## 4. 実装すべき差分（ワークオーダー案）

上から着手。D1+D2で「送れる」、D3で「振り返れる」、D4で「ニーズ評価」まで到達。

| WO | 内容 | 詳細 | 規模 |
|---|---|---|---|
| **D1** | 担当者一覧の抽出UI強化 | `/app/contacts` に絞り込み（会社ステータス/業種/規模/役職・役割/温度感/興味カテゴリ/最終接触日/メール有無）＋チェックボックス＋件数表示。現状は絞り込みなしの読み取り専用テーブル | 中 |
| **D2** | 顧客向け一括メールアクション | `contact-mail.ts`（`lead-mail.ts` の contacts版）。対象解決: contacts×accounts join → メール正規化・重複除外 → `mail_suppressions` 突合 → 同一テンプレ送信済み除外（`email_messages.contact_id`）→ 300件/日次上限。`BulkMailPanel` は対象抽出コールバックだけ差し替えて共通化 | 中 |
| **D3** | セグメント履歴の汎用化 | `lead_mail_batches` に `target_kind ('lead'\|'contact')` と汎用 `filters` を追加（or `mail_batches` へ改名view）。`/app/email/segments` で顧客配信も同列に表示 | 小 |
| **D4** | 企業軸の反応分析 | 企業別 送信/開封/クリック/返信の集計RPC＋企業詳細（`/app/accounts/[id]`）へのメール反応タイムライン表示。「開封率でニーズを数値評価」の本丸 | 小〜中 |
| **D5**（任意） | カテゴリ運用UI | `interest_topics` のタグ編集・一覧絞り込み・タグ別配信実績。前回の「カテゴリ分類」を正式運用に乗せる | 小 |

**マイグレーションは D3 の1本のみ**（`lead_mail_batches` への列追加）。他は既存スキーマで完結する。

## 5. 意思決定が必要な論点

1. **対象単位**: 担当者（contact）単位で送る想定でよいか。同一企業に複数担当者がいる場合に「全員に送る/企業ごと1名（役職上位優先）」の切替を初期スコープに入れるか。→ **推奨: contact単位＋アドレス重複除外のみ（現行リードと同じ）。企業ごと1名は次段**。
2. **リードとの重複送信防止**: 同一人物がリードと顧客の両方に存在するケースで、同じアドレスへ二重に送らないためのクロス突合（email単位で `email_messages` を横断チェック）を入れるか。→ **推奨: 同一テンプレの送信済み判定を lead/contact 横断の「宛先メール単位」に変更（D2に含める・小）**。
3. **カテゴリの持ち方**: 前回の「カテゴリ分類1/2」を (a) 既存 `contacts.interest_topics`（text[]）で運用するか、(b) 企業側にも `accounts` タグを新設するか。→ **推奨: (a) で開始。企業属性は既存の業種/規模/ステータスで代替**。
4. **送信上限**: 送信者ごと日次300通（ドメイン評価保護・2026-07-29運用決定）のままでよいか。顧客ベース配信の想定規模（現状の顧客リスト件数）次第では複数送信者での分担運用を明文化する。
5. **UIの置き場**: (a) 担当者一覧（`/app/contacts`）を強化して送信起点にする（リード一覧と同UX・推奨）、(b) `/app/email/` 配下に「配信先選択」専用画面を新設する。
6. **運用ルール**: 既存取引先への配信は特電法上の同意例外に当たるが、配信停止導線（フッター/ヘッダ）は全配信で維持（既存実装のまま）。スプレッドシート版リスト（Drive）は**CRMへの取り込み後に凍結**し、マスタをCRMに一本化することを運用として合意したい。

## 6. スコープ外（v1）

- HTMLリッチメール・画像埋め込みエディタ（現行はテキスト＋署名。開封計測は既存ピクセルで可能）
- 配信専用基盤（SendGrid等）への移行 — 日次300通×複数送信者で不足が見えたら再検討
- 企業単位のフリークエンシーキャップ（月N通まで等）
- スプレッドシート版データの自動インポート（必要なら別WO: 企業リストCSV→accounts/contacts取込。既存の名寄せ・重複排除 `dedupe.ts` を流用）
